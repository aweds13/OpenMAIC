# 一、宿主与插件（DSH 侧）

## 1.1 插件入口的形状（照这个写，别自创）

- **现象**：插件写完后"没装上"，或工具一个都没出现。
- **真因**：入口必须恰好导出 `name` / `inject` / `apply` 三样，宿主按名字装配。
- **修法/判据**：照抄现成插件。
- **读数原文**（`_tools/dsh-plugins/openmaic-course/lib/index.js`）：
  `:76 export const name = "dsh-openmaic-course"`、`:77 export const inject = ["tools","webServer"]`、`:507 export async function apply(ctx)`、`:83 const SEAM = "/dsh-openmaic"`、`:517 const register = (spec, execute) => { try { ctx.tools.register(makeTool({...spec, async execute(args){ return execute(args||{}); }})); } catch (error) { console.warn(\`[openmaic-course] 工具 \${spec.name} 注册失败：\`, String(error)); } }`。

★ 注意 `:517` 那个 `try/catch`：**注册失败只打一行 warn，工具静默消失**。看到"某个工具不存在"先翻启动日志里的 `注册失败`。

## 1.2 插件入口不能有顶层 await

- **现象**：启动日志出现一次 `Error [ERR_REQUIRE_ASYNC_MODULE]: require() cannot be used on an ESM graph with top-level await`，界面上表现为"插件没装上"。
- **真因**：宿主是 `require()` 装插件的，ESM 图里带顶层 await 就装不了。
- **修法/判据**：所有 `await import(...)` 挪进**函数体**；`apply` 本身可以是 async。惰性解析 `defineTool`（`await import("@deepseek-ai/dsh-tools")`）时尤其容易犯。
- **读数**：错误原文见上。

## 1.3 `parameters` 的形状：作者简写 vs 真 JSON Schema

- **现象**：插件本地注册通过，一到模型侧就 `400 Invalid schema for function 'xxx': schema must be a JSON Schema of 'type: "object"', got 'type: null'`，**而且连累整轮所有工具**（不只那一个）。
- **真因**：`defineTool` 吃 `{type:"json"}` 作者简写；`ctx.tools.register` 裸定义吃**真 JSON Schema**。`parameters` 本身是「参数名 → 该参数的 schema」映射，**不是**一份 JSON Schema。写成 `{type:'object',properties:{...}}` 会被当成名叫 `type` / `properties` 的参数而**整个工具被静默跳过**。
- **修法/判据**：自己写 `toJsonSchema` / `propertyToJsonSchema` / `paramsToJsonSchema`（`openmaic-course/lib/index.js` 自带这三只）。**必填写成参数属性上的 `required: true`**，顶层 `required: [...]` 也被拒。
- **读数原文**：解析器原话 `unsupported JSON schema: parameters.type must be a value schema object`；旧形状里那 4 个报 `parameters.properties.type must be string/number/integer/boolean/null/array/object/json, or use oneOf`。
- 探针 `_tools/dsh-plugins/probe-define-tool.mjs`：照此改完 4 个工具后 **5/6 收**（第 6 个是旧形状对照，本该被拒）。
- ★「别写 `additionalProperties: false`」是**症状不是规定** —— 真原因是整个 `parameters` 被当成了参数名。

## 1.4 宿主注册工具时不校验 `parameters`

- **现象**：参数写错形状，本地**静默通过**，到模型侧才炸，且连累整轮。
- **真因**：`ctx.tools.register` 只校验 `output.schema`，不校验 `parameters`。
- **修法/判据**：注册完自己跑一遍 `assertSupportedJsonSchema(tool.parameters)`。
- **读数**：无独立计数（属机制性结论，已由 1.3 的探针 5/6 间接实测）。

## 1.5 部署副本是 copy，不是 junction —— 改源不会生效

- **现象**：改了 `_tools/dsh-plugins/` 里的源码，行为不变。
- **真因**：`~/.dsh/profiles/desktop/node_modules/` 下这两个插件是**复制体**而不是链接。
- **修法/判据**：改源之后**手动同步到 profile + 重启**。
- **读数原文**：`dsh-openmaic-course` 与 `dsh-openmaic-local-capabilities` 都是 `DIRECTORY (copy)`（`test -L` 为假）。该 `node_modules` 下唯一的 `<JUNCTION>` 是 `probe-seat` → `D:\文档\jelly_ware\program\engineering\gates\diag\probe-seat`，mtime 2026/10/17 21:51。
- ★ **旧结论「`file:` 依赖装出来是 Junction，改源即生效」已被推翻** —— 那对**别的**包成立，对这两个 openmaic 插件不成立（见上）。客户端半本来就一直是预打 bundle，改 `lib/client.src.js` 后必须 `node build.mjs` 重打。

## 1.6 Junction 安装会让插件解析不到 `@deepseek-ai/*`

- **现象**：走 `file:` 依赖装成 junction 时，插件里 `Cannot find package '@deepseek-ai/dsh-tools'`。
- **真因**：Node 按**真实路径**向上找 `node_modules`，junction 指向的源目录在 profile 之外。
- **修法/判据**：插件退回裸 `ctx.tools.register`，就得自己把作者简写翻成 JSON Schema（即 1.3 的 `paramsToJsonSchema`）。

## 1.7 修完必须重启才作数

- **现象**：代码改完了，行为还是旧的，每一轮报同一个错但 `request_id` 是新的。
- **真因**：宿主半只在**启动时**装配。
- **修法/判据**：判断"没修好"之前，先看进程启动时间 vs 代码 mtime。
- **读数原文**：一次实测里进程 `0:06:02` 启动、代码 `0:22:40` 才改完 ⇒ 每轮都用旧 schema。

## 1.8 `cordis.patch.yml` 的装法

- 装法三步：profile 的 `package.json` deps 加 `"dsh-openmaic-course": "file:<本目录>"`；`dsh.profile.bundles` 末尾加同名；**重启**。

  - `_tools/dsh-plugins/openmaic-course/lib/index.js` = **7** 个：`openmaic_active` / `openmaic_courses` / `openmaic_page` / `openmaic_page_text` / `openmaic_patch_stage` / `openmaic_scenes` / `openmaic_search`

## 1.11 用 DSH 原生渲染，不做 iframe

# 二、内容与渲染

## 2.1 行高只有一个来源：渲染器写进 DOM，检查器读同一个数

- **现象**：检查器报"文字装不下"，真渲染却装得下。
- **真因**：同一个常数写在**两个地方**（渲染器 class 里的 `leading-[1.5]`、检查器里的字面量 `1.6`）。库里绝大多数 text 元素**没有** `lineHeight` 字段 ⇒ 全部走回落值 ⇒ 常数错了不是"个别页面错"，是**这一整批结论错**。
- **修法/判据**：`lib/slide/text-metrics.ts` = 唯一来源，`TEXT_LINE_HEIGHT = 1.5` / `TEXT_PADDING_PX = 10`。`BaseTextElement.tsx`（播放路径）与 `TextElement/index.tsx`（编辑器）把 `lineHeight: elementInfo.lineHeight ?? TEXT_LINE_HEIGHT`、`padding: ${TEXT_PADDING_PX}px` **显式写进 DOM**，class 里的 `leading-[1.5]` / `p-[10px]` 删掉；`lib/quiz/layout-check.ts` 直接 import。判据 `tests/components/slide-renderer/text-line-height-pin.test.ts`（6 条）要求渲染 DOM 与检查器回落值同数、且渲染器里不许再出现行高字面量。
- **读数原文**（真 Edge 量 24 个盒子，`p46/fit-flagged.json`）：判据行高 1.2 ⇒ 真溢出 **1** 条；1.4 ⇒ **3**；**1.5（库里生效值）** ⇒ **3**；1.6（原写死）⇒ **19**；1.8 ⇒ **24**。⇒ 用 1.6 判就是 **16 条凭空多出来的"溢出"**。这 24 个盒子里 **0 个**带 `lineHeight`。
- 看得出差别的那一半：20 个汉字 / 20px / 盒宽 200 ⇒ 需要 90px；盒高 92 ⇒ **不报**，盒高 80 ⇒ **报**。
- 复现：`npx vitest run tests/components/slide-renderer/text-line-height-pin.test.ts`；`node D:/文档/jelly_ware/_tools/openmaic/diagnostics/measure-slide-fit.mjs D:/文档/jelly_ware/_tools/openmaic/diagnostics/p46/fit-flagged.json --sheet`。
- 变异（跑完 md5 复原核对）：`TEXT_LINE_HEIGHT` 1.5→1.6 ⇒ 4 条红；class 里 `leading-[1.5]` 加回 ⇒ 2 条红；删 `?? TEXT_LINE_HEIGHT` 回落 ⇒ 1 条红。
- 历史读数（**未重跑**，出自旧文件的 psql）：`text` **1084** 个（带 `lineHeight` 仅 **5**：1.15×1、1.5×4）；`shape` 623（带 `lineHeight` 0、带正文 0）；`latex` 45 / `table` 14 / `line` 4。
- ★ `shape` 那条渲染路径（`ShapeElement` 用 `leading-[1.5]`、`BaseShapeElement` 用 `leading-relaxed` = **1.625**）**潜伏着**不统一；623 个 shape 一个正文都没有，当前不会让检查器算错，**没改**。

## 2.2 「文字装不下」在边界上说了不算 —— 估算的精确率只有 13%

- **现象**：估算器报"装不下"，人工看是好的。
- **真因**：参数错（行高 1.6、可用宽度没减 `padding`）＋ 本质上估算误差两边都有，**没有阈值能分开真假**。
- **修法/判据**：① 参数从 `text-metrics.ts` 取（见 2.1、2.4）；② 改话术 —— 差额 **≤ 一行**时不再冒充结论，直说「可能是装不下 / 这不是结论 / 要渲染确认」；超过一行才照直说是缺陷。
- **读数原文**：估算报"装不下" **23–24 条**，真 Edge 判真溢出 **3 条**（第 50 页 el14 +22px、第 55 页 el10 +22px、第 74 页 el14 +34px），其余 20 条余量只有 **2px** ⇒ 精确率 ≈ **13%**。反例：真溢出第 50 页 el14 估算差额只有 **+12px**，误报第 7 页 el8 却是 **+26px**。
- **不用人工的路只有一条：渲染量。** `measure-slide-fit.mjs --sheet` 量行高敏感度，结论从 3 条一路涨到 20+ 条 ⇒ 这个常数本身就是判据的一部分。
- 读数存档 `_tools/openmaic/diagnostics/p46/slide-fit-truthtable.txt`；判据 `tests/quiz/layout-check.test.ts` 新增 5 条 + **5 道变异全咬**。

## 2.3 「是不是我改坏的」= 改前/改后差集（纯算术，不用人眼）

- **现象**：学习者原话「新增两处盒子高度不足……都是既有问题，我的改动是等长的」。
- **真因**：不是判据错，是工具**没把"改前"记住** —— `patch_stage` 只在写完**之后**算一遍。
- **修法/判据**（`a39adee`）：`patch_stage` 把改动前那一页（`resolved.scene`）一起传进诊断。三部件：
  - `layoutFindingKey()` = 一条发现的**身份** = `code` + 元素下标（**不是 message** —— message 里带估算数字，改一个字就变）。
  - `layoutDelta(before, after)` 纯函数 ⇒ `{ added, removed, kept }`。
  - `formatLayoutDelta()` 人话：没变 ⇒「这次改动**没有引入新的问题**，改前就有 N 处，**不是你这次改出来的**」；有变 ⇒「新引入了 N 处」/「✓ 修掉了 N 处」。
- **读数原文**：`generate_scene` 写新页 ⇒ 不给 `previousScene` ⇒ `layoutDeltaText` 是**空串**（判据钉了这条）。判据 `tests/quiz/layout-check.test.ts` +7 条、`scene-diagnostics-density.test.ts` +3 条，**6 道变异全咬**（身份改用 message / 不带下标 / kept 当 added / removed 恒空 / 既有问题不改口 / 不给 previousScene 也算差集）。
- ★ 通用形状：凡"这个缺陷是不是刚引入的"，都该记住改前那一版再作差。同形状适用：字数带、覆盖缺口、计划依赖。

## 2.4 量尺本身也是第三个来源

- **现象**：`measure-slide-fit.mjs` 量的不是应用画出来的东西。
- **真因**：它自带了**一份**参数且错了两处 —— `padding: hasTextInsets ? 0 : '10px'`（真渲染器**无条件**加内边距，那条分支本部署从来没成立）⇒ 量的盒子比真渲染**宽**；元素没带 `lineHeight` 就什么都不设 ⇒ 浏览器用 `normal`（≈1.25）而不是回落值 **1.5** ⇒ "库值"那一列逐条系统性偏乐观（第 4 页 el11 旧表"余 10px"、真值"**余 4px**"）。
- **修法/判据**：工具改成从 `lib/slide/text-metrics.ts` 读这两个数（正则取 `export const <名字> = <数字>;`），**读不到就报错退出**，不许再自带一份。`--sheet` 自检因此可判：**"库值"那一列必须与 `lh1.5` 那一列逐个数字相同**。
- **读数原文**（`p46/slide-fit-truthtable-2026-10-10-第六段.txt`）：
  `新表：库值 == lh1.5 的行数: 24 / 24`
  `旧表 真溢出条数: 库值=3 · lh1.2=1 · lh1.4=3 · lh1.5=3 · lh1.6=19 · lh1.8=24`
  `新表 真溢出条数: 库值=3 · lh1.2=1 · lh1.4=3 · lh1.5=3 · lh1.6=19 · lh1.8=24`
  `新表里库值真溢出的是: ['第50页 el14', '第55页 el10', '第74页 el14']`
- ★ 教训：「唯一来源」这条规矩对**量尺**同样成立，否则量尺会替检查器背锅。

## 2.5 字号下限只是**诊断**，不是闸

- **真因**：`MIN_READABLE_FONT_PX` 只活在事后检查器里。
- **修法/判据（当前没有闸，仅记录）**：写入路径（`lib/server/agent-runtime/dsl-tools.ts`、元素 schema）**完全不引用它**；只有写完后的 `checkLayout` 会报 `font-too-small`。
- **读数原文**：`lib/quiz/layout-check.ts:42 export const MIN_READABLE_FONT_PX = 14;`、`:352 if (fontPx < MIN_READABLE_FONT_PX)` → `:354 code:'font-too-small'`、`:357` 文案 `${label}的字号是 ${fontPx}px，低于可读下限 ${MIN_READABLE_FONT_PX}px —— `；`dsl-tools.ts:33` 只 import `estimateTextHeightPx, maxFontSizePx`，不含 `MIN_READABLE_FONT_PX`。

## 2.17 「计划工具容量只有 47 条」是模型对着我们的 bug 做规划

这是四层链条，**没有任何一层是"容量"**。按发现顺序：

**第一层：`add` 按 order 静默覆盖。**
- 现象：51 页 / 计划 47 条，缺 order = 37,40,46,47；agent 原话「补一次、洞往后挪一格」。
- 真因：`upsertOutlineEntry` 按 **order** 认身份 ⇒ 往已占用 order 写就是覆盖另一页且不报错。
- 修法：`add` 先做冲突检查 —— 同 order 已有**标题不同**的条目就整批拒绝、一个字不写盘；同标题重写放行、往空 order 写放行。
- 判据：`plan-freeze-add-clobber.test.ts` 4 条 + 变异。
- ★ 弯路：先改 `renumberCourseOrders` 里 `flatMap(… => [])` 结果既有判据变红（「renumbers scenes and outline entries together for reorder and **delete**」）⇒ 完整撤回。**教训：改看起来像 bug 的丢弃逻辑前，先看有没有判据钉着它的语义。**

**第二层：同一身份出现两次 ⇒ "每补一条就挤掉一条，等量交换"。**
- 现象：agent 报「现在 51 条 / 56 页，缺 7,8,9,12,20,52，另有一条 order 15 重复；每补一条就挤掉一条」。
- 真因：`upsertOutlineEntry` 用 `findIndex` 找第一条同 order 替换 ⇒ 同 order 两份时第二条永远碰不到 ⇒ 总数永远不变。
- 修法：① 写时同 order 只保留刚写进去那条；② `plan_freeze status` 直接报出缺号与重号。
- ★ 陷阱：`sameEntry` 的提前返回会绕过去重（内容一样就 `return changed:false`）——"无需修改"的前提要加上"那个 order 上只有一条"。
- **通则**：**"容量不足"先怀疑"同一身份出现两次"。**

**第三层：id 从 order 推出来，页号被平移过 ⇒ id 与 order 脱钩。**
- 现象：用户报「补进 9 条、同时丢掉 9 条，总数恒为 50」。代码里没有任何截断（grep 无命中）。
- 真因：新计划里 `(12,'p5') (18,'p12') (25,'p18') (28,'p21')` 大面积错位，而 `upsertOutlineEntry` **先按 id 认身份** ⇒ 给 order 21 写 `id: p21` 会找到坐在 order 28 上的那条并把它搬走 ⇒ 每次写入都在搬家。
- 读数原文：`backfill` 自称"补了 9 条、原有 50 条一个字没动"，实际 **50 → 53**（进来 9、被偷走 6：21,26,29,31,37,41）。
- 修法：**身份键由调用方选** —— `upsertOutlineEntry(…, { matchBy: 'id' | 'order' })`，默认 `'id'`；`generate_scene` 的 id 是真身份；`plan_freeze` 的 add/backfill/revise-entries 三处一律 `'order'`。
- ★ 存量错位 id 因此无害，**不需要数据迁移**。
- 端到端：修复前 50 → **53**；修复后 50 → **59**（页数 59、无缺、无重复）。
- **通则**：**身份从位置推出来时，位置一变身份就废。**

**第四层（未修）：`revise` 改不了计划，而三处文档都在教模型用它。**
- 现象：提示词、门槛拒绝信息、`freeze` 的回复三处都写「改计划用 `plan_freeze { action: "revise", reason }`」。
- 真因：`revise` 只调 `revisePlan()` 记一次理由，**一个条目都不动**；唯一能写条目的是 `add`。
- 代价：agent 一边拆页一边补条目 ⇒ 条目静默消失 4 条（37/40/46/47）⇒ 它把计划当成"容量只有 47 条"⇒ 据此给学习者做了规划。
- 已修的半：新增 `shiftOutlineOrders(outline, fromOrder, delta)`（"拆页 ⇒ 后面页号顺延"原来没有任何原语能表达）；`revise` 现在接受 `shift` / `removeOrders` / `entries`，回复列出实际改动；只传 reason 时明说"没有改任何条目"。判据 5 条 + 变异（让 shift 不生效 ⇒ 2 条红）。
- **通则**：**一句写给模型的指令就是一份对实现的承诺。**

## 2.19 计划落盘：`upsertOutlineEntry()` 的三个刻意决定

- **接入方式**：`generate_scene` 写页之后，用 `upsertOutlineEntry()` 把同一条 `SceneOutline`（就是喂给内容生成器的那一条）按 **outlineId → order** upsert 进计划。
- 三个决定：
  1. **替换而不是追加** —— 重生成很常见，追加会堆出同 order 的僵尸条目，让 order 兜底匹配配到错的那条。
  2. 写 outline 只能走**全量** `saveDocument`（存储层没有增量 API），所以 `changed: false` 时**跳过整篇保存**。
  3. **不动 `generationComplete`** —— agent 造的课出生就是 `true`，而在该标志下 `mergeStageOutline` 只显示已落盘的页（否则课程列表会凭空多出不存在页）。
- 写 scene 与写 outline 是两次写，中间崩掉的结果就是旧行为（brief 没落盘、页面还在）⇒ 纯改善，无新的坏状态。`details` 里有 `outlinePersisted`。
- **验证要看**：`SELECT jsonb_array_length(data->'outlines') FROM document_outlines` 应 > 0。回归 pin：`tests/agent-runtime/course-outline-write.test.ts`。

## 2.22 练习脚手架：一页课 → VS Code 里真能跑的文件夹

- 用户要求：「创建沙箱或虚拟环境…打代码，正确的话就蹦出某种结果」「**高效结合 vscode**…两个联动到一起」。
- **设计要点：一个通用 runner（我的代码）+ agent 只写数据。** agent 写 `checks.json`（跑什么命令、期望什么），**不生成脚本**。好处：编码坑只修一次；数据可校验（形状错当场拒）而代码不可；换语言不改 runner。
- ★ **编码坑写进 runner**（本机实测 `native.encoding=GBK` / `stdout.encoding=GBK`）：`javac Hello.java` 能编译但中文变乱码。runner 对每条命令**自动补** `javac -encoding UTF-8` / `java -Dstdout.encoding=UTF-8 -Dfile.encoding=UTF-8`。
- ★ **与 VS Code 的联动靠配置，不靠起进程**：`.vscode/settings.json` 钉 `files.encoding=utf8`（java 另加 `java.debug.settings.vmArgs`）、`.vscode/tasks.json` 把"跑判据"设成**默认构建任务** ⇒ **Ctrl+Shift+B** 就能跑。这样 web 服务**不需要"执行任意命令"的能力**。工具返回文本里明说"我没有替你打开 VS Code，也没有执行任何命令"。
- ★ **安全三道纵深**：文件夹名 sanitize → 每个文件路径过 `isSafeRelativePath`（相对/无 `..`/无盘符）→ 兜底 `resolve(target)` 必须在 `resolve(root)` 之下。另：**已存在的练习文件夹默认拒绝覆盖**（他可能正在里面写代码），要覆盖得显式 `overwrite: true`。
- 落点：`课程与学习\练习\<stageId>\<NN-标题>\`。
- ★ **函数级死代码又抓到一次，这次是"两份实现"**：`practiceStageDir` 0 引用，因为工具把同一段逻辑内联重写了一遍 ⇒ 合并成一处（该函数接受 root 参数），并加测试钉住"唯一实现"。**教训：导出的 helper 没人用，往往不是"暂时没用"，而是调用点抄了一份。**
- 回归 pin：`tests/agent-runtime/practice-scaffold.test.ts`（15 条，其中 3 条**真的把 runner 跑起来**：正确 ⇒ exit 0 + `result.json` passed=1；错误 ⇒ exit 1 + problems 含"输出里没有"；java 裸命令 ⇒ 输出含 `javac -encoding UTF-8`）。

## 2.23 练习结果读回：`practice_result`（明说哪一半没做）

- ★ 三个「不许静默」的落点：① 还没跑过 ⇒ 明确说「还没有跑过判据」+ 给出 Ctrl+Shift+B；② `result.json` 坏了 ⇒ 说清并让他重跑；③ 同一页多个练习 ⇒ **列出名字让他指定**，不猜。

- **修法**（插件仓 `9445163`，三处）：① 新增 `elementMarkup()` 返回未剥标签的原文；② 新增 `markupChanged` 桶 —— `elementText` 相同但 `elementMarkup` 不同才进，真改字/真改样式/逐字节相同三种情形全部不受影响；③ 七个变更桶全 0 时，`dryRun` 与非 `dryRun` **两条路径都追加 `note`**：「差集看不见这次改动，但库里字节会变」。
- **判据（五向，差集纯函数直跑）**：markup-only → `textChanged 0, markupChanged 1` ✅ / 真改字 → `textChanged 1, markupChanged 0` ✅ / 真改样式（fontSize 48）→ `restyled 1` ✅ / 逐字节相同 → 全 0 且**无** note ✅ / 只多一个空 `<span>` → `markupChanged 1` ✅。
- ★ **反过来说得通的判据**：看到「`changes` 非空但桶全 0」时，不要判成工具坏了 —— 先是 markup-only 改动；现在它会自己说出来。

### 3.9.1 端到端写库与字节级还原（同一页实测）

## 5.6 反斜杠会被 heredoc 吃掉

- **现象**：写进脚本的正则少了一个 `\`，跑出来行为诡异。
- **真因**：`bash -c` + `<<'PYEOF'` 的引号 heredoc 里，`\\` 会折成 `\`（当次会话被咬 **6 次**）。更精确的规律：
  - python 字符串里 `\b \n \r \t \f \v \a \0` 是**合法转义** ⇒ 被吃掉（`\b` 变退格 0x08，正则里没词边界）；
  - `\s \w \d` **不合法** ⇒ 原样保留（只给 `SyntaxWarning`）。
- **修法/判据**：写含反斜杠的正则**一律用占位符**或 `edit` 工具，不要过 heredoc。
- ★ 连带的读文件坑：`pathlib.read_text()` 的通用换行会把裸 `\r` 翻成 `\n` ⇒ **要数行尾就用 `read_bytes()`**。

## 6.6 上游估算器（pi 的 `estimateContextTokens`）

- 假设：「最后一条 assistant 消息的 usage 描述的就是下一次请求」。
- 压缩只把**锚点之前**的历史换成摘要，锚点自己留在保留尾巴里、连 usage 一起 ⇒ 假设当场失效且**一个字都不报**：显示恒为 `N -> N`、同一个数还喂给 `shouldCompact` ⇒ **每次压缩后必然白压一次**。

## 6.7 `browse_page` 是**间歇性**超时，不是「所有外网都被拦」（2026-10-30 实测，推翻旧说法）

旧说法：「browse_page 在本机被 fake-IP 拦，别当它是坏的」。实测下来这句**只说对了一半**，而且容易让人误判成「结构性不可用」。

- **canary 全过**：`https://example.com` / `https://www.baidu.com/` / `https://github.com/` 全部 `ok`。
- **`https://ocw.mit.edu/` 首次 FAIL**：`Page.goto: Timeout 30000ms exceeded`（`browse_server.py:49` 的 `NAV_TIMEOUT_MS = 30_000`）。
- ★ **但同一 URL 立刻重试就 `ok`**：连跑三次 `https://ocw.mit.edu/about/` ⇒ `ok len=8569` / `ok len=8569` / `FAIL Timeout`。**同一个域名、同一台机器、同一分钟，成败交替。**
- 旁证「网络本身没问题」：`curl` 直连这三个域名全部 `http=200`，`ocw.mit.edu` `t=1.150378s ip=151.101.66.132`（真实 Fastly 地址，**不是** 198.18.x 的 fake-IP）；`nslookup ocw.mit.edu` 回四个真实地址。`ProxyEnable = 0`、环境变量无 `*_PROXY`。
- 结论：这是**首跳冷启动 + 30 s 导航超时**的竞态（Playwright 每次冷起浏览器上下文），不是域名被拦。⇒ **判据不能写成「browse_page 可用/不可用」，要写成「重试一次」**；写文档时别把它归因到 fake-IP（那条只影响 **OpenMAIC 自己的 SSRF 判据**，不影响这个 8730 服务的出站）。
- 排查时别被 `reason` 截断骗到：它 `str(exc)[:300]`，`Timeout 30000ms exceeded` 后面的 `Call log` 会被切一半。
