## 二、怎么起：`start_all.ps1` 的两个 Phase

脚本：`D:/文档/jelly_ware/_tools/openmaic/start_all.ps1`。
`start_all.cmd` 是双击入口：跑同一条，**只在退出码 0 时**才 `start "" "http://127.0.0.1:3000/workspace"`，
然后 pause。所以「浏览器没开」= 启动报了问题，去看上面的输出。
★ 它打开的是 **3000（旧 Web UI）**，而那份 standalone 现在是陈旧的（§3.7）——
日常请另开 `http://127.0.0.1:61123` 的 DSH 面板。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "D:/文档/jelly_ware/_tools/openmaic/start_all.ps1"
```

**幂等**：已在监听的服务报 `already up` 并放过，所以跑两遍无害。

### 2.1 Phase 1 —— 等就绪，秒级

这两个是「可用」的定义，**等**。

| 顺序 | 服务 | 做什么 | 等多久 |
|---|---|---|---|
| 1 | PostgreSQL | `pg_ctl -D <PGDATA> -l <PGLOG> start` | 上限 120 s |
| 2 | OpenMAIC | `npm run dev` | 上限 120 s，**最多重试 3 次** |

期望读数（健康时）：

```
  PostgreSQL       started      port 5433
  OpenMAIC         started      http://127.0.0.1:3000
```

**Phase 1 里两个刻意的反直觉设计，别"优化"掉**：

- **端口钉在 `postgresql.conf`，不用 `-o "-p 5433"`。** 这样脚本、Windows 服务、手敲 `pg_ctl`
  三种启法都和 `DATABASE_URL` 一致。第一版脚本就是因为 PostgreSQL 跑在默认 5432、
  而探针探 5433，把一个健康的库报成 `FAILED`。
- **OpenMAIC 故意不走通用等待逻辑。** `next dev` 会在一秒内 Turbopack panic 而端口永不打开；
  走通用等待就要白等满整个等待窗口才报 `FAILED`，操作者读成"一键启动挂了"。
  现在改为盯 `_openmaic_dev.err.log`，命中 `TurbopackInternalError` / `^FATAL` 就立刻清理 + 重试：

  ```
  Error [TurbopackInternalError]: failed to create junction point at
    ...\.next\dev\node_modules\<pkg>
  Caused by: os error 80 (already exists) / os error 5 (access denied)
  ```

  成因：Turbopack 在 `.next\dev\node_modules` 下留 per-package junction，**优雅退出才删**；
  `Stop-Process -Force`（`stop_all.ps1` 和任务管理器都是）会留下它们。
  清理代码**绝不**用 `Remove-Item -Recurse` / `rmdir /s` —— 那会**跟着 junction 进去删掉
  `node_modules\.pnpm` 里的真包**。它自己走树、不进 reparse point、用非递归 `Directory.Delete` 只删链接。

输出里先出现这一行，然后 6 个服务逐个报：

```

```

```
  <名字>  (<原因>)
  PostgreSQL log: D:\PostgreSQL-OpenMAIC\server.log

```

### 2.3 ★ 真实的坑：陈旧 `postmaster.pid`

**症状**：PostgreSQL 起不来，`start_all` 报

```
  PostgreSQL       FAILED       not ready in 120s
```

而 `D:/PostgreSQL-OpenMAIC/server.log` 里没有崩溃记录。

**原因**：`postmaster.pid` **文件存在**，但它第一行那个 PID 早就死了（上次硬关机 / 强杀留下的）。
`pg_ctl start` 看到 pid 文件就认为"已经在跑"，直接退出，什么都不做。

**判据是「文件在」不等于「进程在」，必须验死活。** 四步，一步一步敲：

```powershell
# ① 取出 pid 文件里的 PID（第一行就是）
Get-Content "D:/PostgreSQL-OpenMAIC/data/postmaster.pid" -TotalCount 1
```

```powershell
# ② 验这个 PID 还活着吗
Get-Process -Id <上一步的PID>
```

- **报错** `Get-Process : Cannot find a process with the following process ID: <PID>`
  ⇒ 进程已死 ⇒ **pid 文件是陈旧的**，继续第 ③ 步。
- **打印出进程信息** ⇒ 库其实在跑，**不要动 pid 文件**；回去查端口/`DATABASE_URL` 对不对。

```powershell
# ③ 把陈旧 pid 文件改名让开（mv 是 Move-Item 的别名；带日期，别删，留证据）
cd "D:/PostgreSQL-OpenMAIC/data"
mv postmaster.pid postmaster.pid.stale-2026-10-30
```

```powershell
# ④ 重新起，然后验
& "D:/PostgreSQL-OpenMAIC/pgsql/bin/pg_ctl.exe" -D "D:/PostgreSQL-OpenMAIC/data" `
    -l "D:/PostgreSQL-OpenMAIC/server.log" start
```

期望读数（第 ④ 步）：

```
waiting for server to start.... done
server started
```

期望读数（独立复核，别只信 `pg_ctl` 自己说的话）：

```powershell
& "D:/PostgreSQL-OpenMAIC/pgsql/bin/pg_isready.exe" -h 127.0.0.1 -p 5433
```

```
127.0.0.1:5433 - accepting connections
```

★ **停库要用 `pg_ctl stop -m fast`，不要 `Stop-Process`。** `stop_all.ps1` 就是为了这个存在的：
硬杀会留下 unclean shutdown，下次启动要跑 crash recovery（日志里是
`was not properly shut down; automatic recovery in progress`），也就是下一条陈旧 pid 的来源。

## 三、怎么跑生产构建 + 上线口径

### 3.1 前置：`install` 之后必须**再跑一次** `build:packages`

`pnpm install` 的 `postinstall` 就是 `pnpm run build:packages`，但**它是并跑的**。
实测 `@openmaic/renderer` 会在 `@openmaic/dsl` **之前** build：

```
@rollup/plugin-typescript TS2307: Cannot find module '@openmaic/dsl'
```

⇒ renderer 的 `dist/*.d.ts` 是残的，`tsc` 报**假错**：

```
Module '"@openmaic/renderer"' has no exported member 'SlideEffects'
```

修法就是按依赖序重跑一次（`build:packages` 里 `@openmaic/dsl` 明确排在 `@openmaic/renderer` 前面）：

```powershell
corepack pnpm run build:packages
```

★ **`pnpm` 不在 PATH 上，一律写 `corepack pnpm`。**
`corepack enable pnpm` 会 **EPERM**（要写 `C:\Program Files\nodejs`，没权限）。

验证：

```powershell
npx tsc --noEmit -p tsconfig.json
echo "EXIT=$LASTEXITCODE"
```

期望读数：`EXIT=0`。（`dist/` 与 `node_modules/` 都是 gitignore 的，不进提交。）

### 3.2 `.env.local` 里的 `MODEL_ROUTES` 必须**保持注释态**

1.2.0 的 server-first 模型配置不再接受它。只要它存在且**没有** `openmaic.yml`，**启动即拒**：

```
[boot] Invalid server configuration; the server will not start: MODEL_ROUTES does not carry over to the
model configuration: write the per-stage models as slots in openmaic.yml (or the file named by
OPENMAIC_CONFIG) and remove MODEL_ROUTES
```

（抛点：`lib/server/model-config/deployment-layer.ts:160` `if (process.env.MODEL_ROUTES?.trim()) throw new LegacyRoutesError();`，
异常类在同文件 `:43`；前缀 `[boot] Invalid server configuration; the server will not start:` 由
`lib/server/boot-failure.ts:40` 加。）

等价物是 `openmaic.yml` 的 `slots:`。本部署**没建 yml** ⇒ 走 legacy 翻译，
`DEFAULT_MODEL=deepseek:deepseek-v4-flash` 仍生效，`agent` 槽默认继承 `llm` 槽（行为不变）。

验证（现在应当是「只在注释里出现」）：

```powershell
cd "D:/文档/jelly_ware/program/OpenMAIC"
Select-String -Path .env.local -Pattern '^\s*MODEL_ROUTES\s*='
```

期望读数：**零命中**。若命中，把它删掉或行首加 `#`，再重起。

### 3.3 `openmaic.yml` 一旦建了就是**整体替换**

`deployment-layer.ts` 头注释写明：「文件存在就用它，不再翻译 env 的 providers / `DEFAULT_MODEL` /
`MODEL_FALLBACK`」。⇒ 想用 yml 必须把 providers **全部**写进去，否则模型全掉。
**现在刻意不建。** 除非你准备好一次把整份配置写完，否则别 `New-Item openmaic.yml`。

### 3.4 构建三步（缺一不可）

★ 每一步都是在仓库根 `D:/文档/jelly_ware/program/OpenMAIC` 下，用 **git-bash** 跑
（PowerShell 等价写法见每步下面）。`next.config.ts` 里是 `output: 'standalone'`，
所以产物落在 `.next/standalone`。


期望读数：末尾 `✓ Compiled successfully` / 无 `Failed to compile`。耗时几分钟。

## 四、怎么建 worktree 并让它真能跑

### 4.1 为什么必须隔离

`git add <单个文件>` **不安全**：两个窗口都在改同一个文件时一样会互相卷。
实测过一次：两个窗口共用主树、都在改 `AGENTS.md`，一次 `git add AGENTS.md` 把对方那段一起提交了，
提交信息只讲一件事、内容多了一整节。**根治靠隔离，不靠更小心的 add。**

### 4.2 建

```bash
cd D:/文档/jelly_ware/program/OpenMAIC
git worktree add ../OpenMAIC-<主题> -b <分支>
```

期望读数（`git worktree list`）：

```
".../program/OpenMAIC"        5677a9f [my-extensions]
".../program/OpenMAIC-<主题>"  5677a9f [<分支>]
```

### 4.3 ★ 新建的 worktree 是**开不起来**的：还差四步

`git worktree` 只给一份干净的**源码检出**，`.gitignore` 里的东西一概没有。

**第 1 步 · `.env.local`（必需）**

```bash
cp ../OpenMAIC/.env.local .
```

不做的后果：没有 `DATABASE_URL`，应用起来也是残的。

**第 2 步 · `node_modules`（必需）**

```bash
corepack pnpm install --frozen-lockfile
```

两个已知现象，都**不是失败**：

- `pnpm` 不在 PATH 上 ⇒ 必须 `corepack pnpm`（`corepack enable pnpm` 会 EPERM）。
- **`postinstall` 会失败**：它调 `pnpm run build:packages`，而那个脚本内部调**裸 `pnpm`** ⇒
  `'pnpm' 不是内部或外部命令`。**依赖其实已经装好了**（pnpm 走全局 store 硬链接，快且不占额外磁盘），
  只是**工作区包没构建**。

补构建，两种绕法：

**(a) 同 commit 时直接从主树拷产物**（最省事；两边 commit 相同时产物等价）：

```bash
for p in mathml2omml pptxgenjs @openmaic/dsl @openmaic/generation \
         @openmaic/storage @openmaic/importer @openmaic/renderer @openmaic/editor; do
  rm -rf "packages/$p/dist"
  cp -r "../OpenMAIC/packages/$p/dist" "packages/$p/dist"
done
node scripts/sync-maic-importer.mjs      # 把 importer 的 bundle 放进 public/vendor/
```

**(b) 自己造一个 `pnpm` shim 放进 PATH**（源头解决，但要自己维护）：

```cmd
@echo off
node "C:\Users\asus\AppData\Local\node\corepack\v1\pnpm\10.28.0\bin\pnpm.cjs" %*
```

### 4.7 一条**没实测过**的注意

**用的时候验一下**：开 `:3001`，看左边课程数是不是和 `:3000` 一样。
不一样就是这条成立，那第二个窗口得手动带上 owner。

## 六、怎么读测试结果

**并跑读数是噪声，不是判决。** 这是本机最贵的一条教训，实战读数如下：

- 定向套件并跑（`tests/agent-runtime tests/generation tests/export tests/slide-renderer tests/server tests/edit tests/components`）：
  **4419 通过 / 58 失败 / 36 个文件**（4632 条）。
- 那 36 个文件**顺序复跑**（`--no-file-parallelism`）⇒ **只剩 6 条真失败**。
- 6 条里修好 4 条，剩下 2 条是**纯环境、不是回归**。

同一批文件"并跑红、单跑绿"的实例（都实测过）：

- `tests/export/use-export-html.test.ts` + `tests/agent-runtime/agent-driver-model.test.ts`
  单独跑 **32/32 绿**，并跑红。
- `tests/agent-runtime/docs-map-coverage.test.ts` 同形。
- `tests/components/slide-renderer/editable-code-element.test.ts` 并跑 30 s 超时、单独 **11 s 绿**。

⇒ **判「是不是语义问题」必须单文件跑或顺序跑一次。** 在并跑读数上做结论一律无效。

红的必须分**三类**（每类都要给对照读数）：

| 类 | 怎么认出它 | 处置 |
|---|---|---|
| **真失败** | 单跑仍红，且与改动相关 | 修 |
| **环境噪声** | 并跑红、单跑绿；或超时类 | 提高超时 / 加 `--no-file-parallelism`，不改判据 |
| **基线同样红** | 在干净的 `origin/main` worktree 上红**同样条数** | 不修，记进结论库 |

**基线的判据做法**：`git worktree add --detach <tmp> origin/main`，再用
`New-Item -ItemType Junction` 借主树 `node_modules`（见 §4.4），跑同一条命令比条数。

两条已知的**本机环境**失败，别再当回归查：

- `tests/server/model-config/{llm-transport,settings-route}.test.ts`：本机 DNS 是 Clash fake-IP
  （`api.openai.com` → `198.18.1.127`），`ipaddr.js` 判 `reserved` ⇒ `lib/server/ssrf-guard.ts:183` 的
  `isNeverAllowedRange` **永远拒**，连 `ALLOW_LOCAL_NETWORKS=true` 也不放开（那个标志只放开 private / CGNAT）。
  这两个文件与 `origin/main` **逐字节相同** ⇒ 上游 CI（真 DNS）是绿的。
- `tests/server/instance-secret-check.test.ts` 类：`chmod 0o500` 造"不可写目录"是 POSIX 语义，
  Windows 上 `dataDirWritable` 仍为 true ⇒ 按 `process.platform === 'win32'` 跳过。

★ **"判据全绿"也可能是假绿灯。** 实例：一个用 `join()` 得到反斜杠路径、再用 `.endsWith('/route.ts')`
过滤的覆盖矩阵测试，在 Windows 上**扫出 0 个入口**却报绿。判据必须能证明它**看得到东西** ——
打「这次实际检查了 N 条」，**N=0 同样算失败**。
