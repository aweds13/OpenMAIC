# 文档架构

> 这份文档解释 `docs/` 为什么长成这样。**它本身不是五层中的任何一层**，是给写文档的人看的说明。
> 判据：`python -X utf8 scripts/check-layers.py`，末行必须是 `LAYER CHECKS: PASS ✅`。

## 一、为什么要分五层

五层不是五个文件夹，是**五个问题的落点**。同一句话放错层，就会在别人改代码时变成噪声或变成谎言。

| 层 | 回答的问题 | 删掉代码还成立吗 | 谁在读 |
|---|---|---|---|
| `intention/` | **为什么做**这件事 | 成立 | 决定要不要做的人 |
| `specification/` | 必须做到**什么** | 成立 | 写代码的人、验收的人 |
| `contracts/` | 怎样才算**真做成**（两边各自实现还能对上） | 成立 | 联调的人、review 的人 |
| `implementation/` | **哪个模块**负责 | 不成立（跟着代码变） | 改代码的人 |
| `taste/` | 什么算**好** | 成立 | 评审时吵架用 |

判断方法：把这段文字拷到一张纸上，合上电脑，它还成立吗？成立且回答「为什么」→ 意图层；回答「必须怎样」→ 规格层；回答「怎么验」→ 契约层；必须开着编辑器才能看懂 → 实现层；只在评审时说「这不是我想要的风格」→ 品味层。

## 二、三条硬规矩

1. **一层只引用上一层，不反向引用。** 规格可以引用需求编号，实现可以引用规格编号；反过来不行 —— 需求文档里写「这个函数在 `runner.ts:2022`」就等于把需求钉死在当前实现上。
2. **跨层关联走索引，不写正文。** `N → SR` 的唯一关联点是 `specification/traceability.md`；`SR → 模块` 的唯一关联点是 `implementation/traceability.md`。正文里不写「这条来自 N 几」。
3. **同一份事实只留一处，其余写指针。** 比如「能力注册原则」的正文只在 `specification/domains/F8-tool-registration.md`；`AGENTS.md` 里只留一行指针和命令。

## 三、升级信号（什么时候该补一层）

不是每个项目都要五层齐全。**最小可行只要意图 + 实现两层**。出现下面任一信号，才补对应层：

| 信号 | 补哪层 |
|---|---|
| 出现第二个使用者/客户端（同一份数据两个入口） | 契约层 |
| 同一行为在两处实现开始不一致 | 规格层 |
| 返工的原因是「没人知道边界在哪」 | 契约层 |
| 只凭口味吵架（「就是不好看/不好用」） | 品味层 |
| 需求来源说不清（「这个功能谁提的、为什么」） | 意图层 |

本项目（OpenMAIC 二开 + 换宿主）的现状：**五层全触发** —— DSH 与旧 Web UI 是两个客户端（契约层）；`course_search` / `read_document` 曾在三处注册点口径不一致（规格层）；写入闸被闸住后不知道该补还是该删（契约层）；阅读页「假控件」是纯口味但反复返工（品味层）。

## 四、域与编号

- **N 编号**（`intention/needs.md`）：一条需求一个号，**只增不改**。砍掉的写法是保留编号并标注「已砍」，不是删号（删号会让所有下游引用断掉）。
- **F 编号**（十个功能域）：按「一块能被单独验收的行为」切，稳定不变。
- **SR-F{域}.{序}**：规格条目，挂在域下。
- **SR-NF{序}**：横切条目，不属于任何单一域。
- 域文件**两层同名对位**：`specification/domains/F1-content-density.md` ↔ `contracts/domains/F1-content-density.md`。名字必须一致，检查器按 F{i}-*.md 这个通配规则匹配（按编号取，不按名字取）。

## 五、每层应该有什么

**`intention/needs.md`**
- 每条需求：编号、一句话、**依据**（谁在什么场景下被什么坑到了，带数字最好）、**不做什么**。
- 不写实现方案。不写文件名。

**specification/domains/ 下的逐域规格文件**
- 用「必须 / 不得 / 当…时」写，不写「建议」「尽量」。
- 每条 SR 一段：规则、为什么是这条线（依据 N）、反例（什么写法违反它）。
- 不写文件名和函数名。

**contracts/domains/ 下的逐域契约文件（与规格层同名对位）**
- 这条 SR **怎么验**：输入、期望输出、失败长什么样。
- 两边（DSH 插件 / 旧 Web UI / 工具 / API）各自要满足什么。
- 可以写测试文件名 —— 那是判据的落点。

**`implementation/modules.md`**
- 哪个模块负责哪条 SR，文件路径到行。
- **可以**写文件名、函数签名、常量值。

**`taste/`**
- 审美与优先级的取舍。写「宁可 X 也不 Y」这类判断。
- 允许主观，但必须给出可执行的判据。

## 六、和仓库里其它文档的关系

| 文件 | 它的位置 |
|---|---|
| `AGENTS.md` | **不是**五层之一。是给 agent 的作业指导（改哪一层、坑、证据命令）。只留规则与指针，正文搬到 `docs/` 或 `复盘/`。 |
| 意图层的通俗版 | 已并入 `intention/needs.md`（N1–N23 就是那份通俗版的编号形态）。 |
| 使用手册 | 已并入 `contracts/interactions.md`（OP-1…OP-6 的「怎么说」）与 `implementation/自检.md` §5。 |
| 实现层的图解版 | 已并入 `implementation/架构图.md`（同名，保留了 ASCII 图与八段说明）。 |

> 三份仓根文档（二开说明 / 怎么用 / 架构图）已于 2026-10-30 删除 —— 内容不是消失了，是**拆进了它各自该在的层**。要看旧版：`git show <那个提交>:<文件名>`，提交号 `490259c1` 是删除前的最后一版。
| `复盘/新窗口交接卡.md` | **状态**，不是规格。按日期倒序追加，最新的在末尾。 |
| `复盘/已结案结论.md` | 踩过的坑与量过的数。**结论库**，不承担教导职责。 |

**一句话分工**：`docs/` 回答「应该怎样」；`复盘/` 回答「当时实际发生了什么」；`AGENTS.md` 回答「动手前先看什么」。

## 七、维护约定

- 改了行为就改对应层的文档；**只有一层需要改**，这是分层的意义。
- 新增需求 → 先在 `intention/needs.md` 加 N，再在 `specification/traceability.md` 挂 SR，最后在 `implementation/traceability.md` 挂模块。三步缺一，`check-layers.py` 会红。
- 砍需求 → 编号保留，正文改成「已砍（原因，日期）」。
- 每次改动跑 `python -X utf8 scripts/check-layers.py`。
