# F8 工具注册与提示词口径

## 域的范围

管「一个能力该不该出现在模型眼前」这条路的约束：没配的能力根本不出现，出现了就必须真能调，多个注册点说同一句话。
不管具体能力的判定逻辑（F5 的检索、F6 的抓取），也不管上下文的组成（F7）—— 只管**注册面与提示词面的口径一致**。

## 规格

### SR-F8.1 外部 MCP 连不上时必须只记录失败，不得注册其工具、不得阻塞会话

**规则**：建立会话时逐个尝试外部 MCP 服务，连不上的必须记进失败清单并继续，不得抛出、不得重试到超时、不得让整场会话起不来。连不上那个服务的工具一个都不得注册，其名称不得进入工具表、允许表与提示词。仍然是「连不上」而不是「配置错误」时，失败必须可归因到是哪个服务、什么原因。

**为什么是这条线**：外部服务不可用是常态，不是异常。一个挂掉的 MCP 服务有两条错误的处置方式：其一，把会话一起拖死 —— 用户为了用一个本地检索功能，被一个跟自己无关的外部服务挡住；其二，把工具注册上但一调就失败 —— 那是模型唯一无法理解的不可用，它会持续重试一个永远失败的工具，直到把上下文耗光。

**违反长什么样**：一个 MCP 服务端口没开，整场会话在建立阶段抛错；或者会话起来了，工具表里躺着一个每次调用都返回「未配置」的外部工具。

### SR-F8.2 未配置的能力不得注册工具

**规则**：能力的配置缺失时，其工具必须不出现在工具表里。不得注册一个「存在但恒返回未配置」的工具作为所谓的默认安全值。「看」与「存」这类配套能力必须同进同退：注册其中一个就必须注册另一个，缺一个就两个都不注册。

**为什么是这条线**：工具表是模型对「我能做什么」的全部认知。一个永远失败的工具不会让模型变得谨慎，只会让它反复尝试 —— 它没有任何依据判断这个失败是暂时的还是永久的。配套能力同进同退的理由更直接：只给检索不给展开，模型能查到片段却翻不开原文，于是只能拿片段当全文回答，这比完全没有这个能力更糟。

**违反长什么样**：服务地址没配，工具仍然注册，描述里写着「查询本地课程库」，一调用返回「未配置」。

### SR-F8.3 未注册的工具名不得出现在提示词与允许表里

**规则**：提示词里提到的每一个工具名、允许表里的每一个工具名，都必须来自**本次真正装出来的工具集合**，不得手写第二份清单。允许表必须由工具表派生，提示词里的工具段落必须在对应能力缺席时整段不出现（不是出现但为空）。工具描述里也不得提及未注册的工具名。

**为什么是这条线**：一份手写的清单就是一份会漂移的清单 —— 它写在注册逻辑旁边，改注册逻辑的人不会记得改它。曾经的形态是：提示词里列了工具名，工具表却是空的；模型照着提示词去调，调用直接失败，而失败原因跟提示词说的完全对不上。允许表与提示词都从同一个集合派生，「说得出的就调得到」才是结构上成立的，而不是靠人记得同步。

**违反长什么样**：某个能力没配，提示词里仍有一段「你可以用 xxx 工具查资料」，而工具表里没有它。

### SR-F8.4 同一能力在多处注册点必须同一口径（配置在则有，配置无则无）

**规则**：同一能力在每一处装配工具的地方都必须用同一条判据决定注册与否 —— 配置在则处处在，配置无则处处无。不得出现「这处按配置判、那处无条件注册」「这处按配置判、那处的注释还写着『不配也注册，返回未配置更安全』」这类分叉。判据必须只有一处定义，其余注册点引用它。

**为什么是这条线**：注册点不止一处 —— 主运行面一处、会话接口一处、子代理装配一处。曾经其中一处无条件注册三个工具，直接让上游的 9 条断言变红，因为子代理的提示词里出现了本部署根本没有的能力名。三处各自判断时，任何一次改动都只会在其中一处生效，而症状会出现在离改动最远的那一处。

**违反长什么样**：主运行面按配置决定注不注册，子代理装配处无条件注册，于是子代理在提示词里看到主代理看不到的工具名。
