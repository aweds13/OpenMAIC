## 1. 一句话结论

**单一真源应当是 Postgres：`owner_material` 一张材料表 + `material_folders` 一层文件夹 + `agent_session_material_links` 一张挂载表，字节的唯一入口是 asset pool（principal `owner:<id>`、引用根 `('material', <material id>)`）。**

我方文件型材料库（`OPENMAIC_MATERIALS_DIR` 下的 INDEX.md + topic md 文件）**不再作为第二真源**，降级为**导入/导出通道**：目录可以被写入、被扫描、被一次性导入，但库的权威状态只在 PG；系统的任何读路径都不再从目录直接取正文（今天的 `listMaterialText()` / `resolveMaterialsIndex()` 直接注入必须改掉）。

三条配套判断：

1. **字节存池，不存 `<cwd>/data` 的新材料。** 今天 `LocalMaterialByteStore` 的 root 硬编码为 `resolve(process.cwd(), 'data')`（`lib/server/materials/bytes.ts:35-40`），而池的字节默认落在 PG 的 `asset_blobs.bytes`（BYTEA），只有配了 `ASSET_S3_BUCKET` 才落 S3（`lib/persistence/asset-byte-store.ts:11-15`）。统一后 `oss_key` 这条斜路只保留**过渡读**（存量行 + 会话副本），新写入一律入池。
2. **owner 作用域靠「principal 派生 + 写栅栏」两件套**，不靠调用方自觉：`assetPrincipalForOwner()` 纯服务端派生（`lib/persistence/owner-assets.ts:62-67`），每个写事务第一条语句取 owner 的共享 advisory lock（`lib/persistence/owner-merges.ts:308-325`）。
3. **会话挂载与库材料是两个概念，都必须保留**：库材料是「owner 名下的一份东西」，挂载是「某个会话现在能看到它」。挂载表不复制字节、不记 owner，靠 join 双方 owner 当场校验（`lib/persistence/session-material-links.ts:2-33`）。

## 2. 现状双系统对照表

### 2.1 两套系统各是什么

- **系统 A（上游 PG 材料库，RFC #1716）**：`lib/persistence/owner-materials.ts`（1386 行）+ `material-library.ts`（593）+ `material-roots.ts`（149）+ `session-material-links.ts`（463）+ `owner-material-extraction.ts`（572）+ `material-extraction-format.ts`（36）；DDL 以 TS 字符串常量内嵌，经 `applySchemaMigrations` 演进到 v5（`lib/persistence/owner-materials.ts:200-349`）。**全仓没有任何 .sql 迁移文件**（`find . -name "*.sql"` 在排除 node_modules 后返回空；`grep -rn "owner_material|material_folders" --include=*.sql` 返回空），这是「表结构唯一来源在 TS」的证据。

### 2.3 失败模式清单（两套各自的坏法）

系统 A：

1. **classic 与 pool 两条字节路径并存**，同一张表同一时刻有两种「字节在哪」的答案；`deleteMaterial` 在提交后才删 legacy 字节，失败只 warn（`material-library.ts:530-545`），靠下次启动 `removeDeletedOriginals` 兜（`migrate-to-pool.ts:294-334`）。
2. **v2 把 `asset_id` DROP 掉、v5 又 ADD 回来**（`owner-materials.ts:230-232` 与 `:266-278`），历史迁移不可重放；老库的实际列状态取决于跑过哪几版。
3. **`retention` 是死列**：迁移保留、注释明说「no runtime membership, processing or lifecycle semantics」（`owner-materials.ts:351-360`）——谁按它写业务都会被静默忽略。
4. **抽取状态机有两套**：classic（`ready`/`extracting`/`resultKey`）与 owner 级（`idle/pending/running/done/failed`），靠 `CLASSIC_EXTRACTION_SQL` 在每条 SQL 里分叉（`material-extraction-format.ts:19-22`），任一处漏写就把 classic 行当新格式处理。
5. **会话副本与 link 的遮蔽规则**：同 id 时会话行优先（`material-resolver.ts:1-33`），`listLibrary` 用 `NOT EXISTS(... agent_session_materials ...)` 排除被遮蔽的 id（`session-material-links.ts:283`）——两处判据必须同步，否则库页会列出读不到的项。
6. **`agent_session_material_links.material_id` 没有外键**（`session-material-links.ts:53-60`），指向一行被真删的资料时 link 变悬空，读取时才以 unavailable 失败。
7. **`deleteOwnerMaterial` 与 `deleteMaterial` 语义相反**（真删 vs 墓碑），谁调用哪个决定数据能不能回来。

系统 B：

8. **没配 `OPENMAIC_MATERIALS_DIR` 就整层消失**（`config.ts:127`），工具、索引、URL 信任闸全部静默降级，没有任何启动告警。
9. **读失败返回空串、绝不抛**（`materials-library.ts:100-111` 注释说明是为「建会话那一个事务」保命）——盘掉了、权限错了，模型看到的是「材料库是空的」，人看不到任何错误。
10. **正文无上限地拼进 prompt**：单文件 200k 字符，`listMaterialText()` 把所有主题文件拼成一段注入（`materials-library.ts:100-111`），没有总量上限，也没有 token 预算。
11. **并发写丢数据**：append 是「读全文 → 拼 → 写回」，两个并发调用后写者覆盖前者；`mkdirSync` 之外没有任何锁。
12. **无归属**：任何能进这个进程的人/会话读到的是同一份目录，越权在结构上无法拦（这正是 00-决策记录 D2「分库结构性防越权」想解决的事）。
13. **无标识、无版本**：改名主题 = 换一个文件；同内容两份不能被识别；无法引用「材料 X」。
14. **裸文本直出**：文件型库把正文直接拼进提示词，没有 nonce 围栏（00-决策记录 D6 点名的「当前最实际的一个漏洞」）。

## 3. 统一后的数据模型

### 3.1 总览

统一后只有 **一个材料表 + 一个文件夹表 + 一个挂载表 + 池的三张表**，外加一张**可选**的检索表：

```
owner_material            ← 唯一材料表（源 + 衍生物 + 导入的 Markdown）
material_folders          ← 一层深文件夹（owner 作用域）
agent_session_material_links ← 会话挂载（只记 (session_id, material_id)）
asset_blobs / asset_entries / asset_root_refs ← 池（字节 + principal + 保活根）
material_chunks           ← 可选：正文切块（D3/D5 落地时才建）
```

`agent_session_materials`（会话副本）**冻结、不再新增**，作为历史读路径存在（见 5.6）。

### 3.2 `owner_material`（统一后的字段表）

列序沿用 `OWNER_MATERIAL_COLUMNS`（`owner-materials.ts:389-403`），但删掉死列与 classic 列。下表「处置」列：**留** = 原样保留；**改** = 语义收紧；**新** = 本次新增；**废** = 迁移后不再读写。

| 字段 | 类型 | 处置 | 用途 | 不变式 |
|---|---|---|---|---|
| `id` | TEXT PK | 留 | 材料 id，`mat_` + 26 位 base32 | 由服务端生成并校验（`material-id.ts:7-11`）；一经分配永不变；claim 搬 owner 时不改 id（`owner-merges.ts:11-27`） |
| `owner_id` | TEXT NOT NULL | 留 | 归属 | 只能由栅栏下的 claim 改动；所有读写 WHERE 必带；无 FK 到 owner 表（owner 由 auth 派生，不落库） |
| `kind` | TEXT NOT NULL | 改 | `source` / `web` / `image` | 值域 CHECK 收紧；`image` 必须 `derived_from IS NOT NULL`；`source`/`web` 必须 `derived_from IS NULL` |
| `derived_from` | TEXT | 留 | 衍生物指向源 | 只能指向同 owner 的 `kind='source'` 且未删的行；衍生物**永不单独移动/挂载/抽取** |
| `mime` | TEXT | 留 | 内容类型 | 决定 mediaKind（`audio/`/`video/` → media，`owner-materials.ts:436-440`）与是否可抽 |
| `bytes` | DOUBLE PRECISION NOT NULL | 留 | 原始字节数 | ≥ 0；等于池 entry 的 `byte_size`；上传预留期间只允许变小（`owner-materials.ts:659-681` 的 `bytes >= $2`） |
| `original_name` | TEXT | 留 | 上传时的文件名 | 改名只写 `display_name`，永不覆盖它（`material-library.ts:410-446`） |
| `display_name` | TEXT | 留 | 改名后的显示名 | 空 = 未改名；`name = display_name ?? original_name ?? id`（`library-view.ts:64`） |
| `asset_id` | TEXT | 改 | 池 entry 指针 | 迁移后 **NOT NULL**（`status='ready'` 时）；发布只发生一次、绝不替换已有指针（`owner-materials.ts:719-764` 的 `asset_id === null` 校验）；必须带 `('material', id)` 引用根 |
| `sha256` | TEXT | 留 | 内容摘要 | `ready` 时 NOT NULL；导入/回填按它做幂等与防篡改（`owner-material-bytes.ts:82-91`） |
| `status` | TEXT NOT NULL | 改 | `uploading` / `ready` | 只两态；`uploading` 行不参与任何列表/挂载/抽取；24h 回收（`owner-materials.ts:464,507-523`） |
| `folder_id` | TEXT | 留 | 一层文件夹 | NULL = Unfiled；非 NULL 时 `(owner_id, folder_id)` 必须命中 `material_folders`（FK 已保证） |
| `created_at` / `touched_at` / `deleted_at` | DOUBLE PRECISION | 留 | 时间戳 | `deleted_at` 非空 = 墓碑；墓碑行对所有解析不可见 |
| `extraction_result` | JSONB | 留（改名 `result`） | 最近一次成功抽取结果 | 与 `status='done'` 同一条语句写入 ⇒ 不存在「done 无结果」；`revision` 就是发布它的 claim token（`owner-material-extraction.ts:1-58`） |
| `extraction_token` / `extraction_claims` / `extraction_lease_at` / `extraction_error` | TEXT/INT/DOUBLE/TEXT | 留 | 领取令牌 / 预算 / 租约 / 失败原因 | token 每次 claim 新铸，旧持有者无法 publish；claims 上限 3，耗尽判 failed 而非永远领取（`owner-material-extraction.ts:73,256-319`） |
| `extraction` | JSONB | 废 | classic + 新版混装的状态袋 | 统一后由 `result` + 上述列表达；只保留只读兼容视图 |
| `oss_key` | TEXT NOT NULL | **废** | legacy 对象 key | 过渡期只读；迁移完 drop（见 5.1） |
| `retention` | TEXT | **废** | 无运行时语义的死列 | 直接 drop，不写业务 |
| `extraction_worker` / `extraction_heartbeat_at` | TEXT/DOUBLE | 废 | v3 的旧租约列 | 由 `extraction_token` + `extraction_lease_at` 取代 |

**表级不变式**

- I1：`kind='source'` 的行是唯一可被挂载、可被抽取、可被移动的实体；衍生物只随源移动（`material-library.ts:23-32`）。
- I2：任何 `status='ready'` 且未删的 source 行必须恰好有一个 `asset_id` 与一条 `asset_root_refs(root_kind='material', root_id=id, asset_id)` 记录；两者在同一个事务里出现（`material-roots.ts:87-149`）。
- I3：墓碑行（`deleted_at IS NOT NULL`）不得被任何解析返回；`deleteMaterial` 提交后字节才删（`material-library.ts:530-545`）。
- I4：`bytes` 与池 entry 的 `byte_size` 一致；漂移即视为损坏，读侧拒绝返回（`owner-material-bytes.ts:82-108` 的摘要校验是同一条思路）。

### 3.3 `material_folders`

沿用 v5 DDL（`owner-materials.ts:266-349`），但收紧两点：

```sql
CREATE TABLE material_folders (
  owner_id         TEXT NOT NULL,
  id               TEXT NOT NULL,
  name             TEXT NOT NULL,
  normalized_name  TEXT NOT NULL,
  created_at       DOUBLE PRECISION NOT NULL,
  updated_at       DOUBLE PRECISION NOT NULL,
  PRIMARY KEY (owner_id, id),
  UNIQUE (owner_id, normalized_name)
);
ALTER TABLE owner_material ADD CONSTRAINT owner_material_folder_fk
  FOREIGN KEY (owner_id, folder_id) REFERENCES material_folders (owner_id, id) ON DELETE RESTRICT;
```

- **保留一层深**：教学材料的组织需求是「几堆东西」，不是目录树；一层深让「移动」是一次 `UPDATE`，删除文件夹是「清空 filing + 删一行」，不需要递归（`material-library.ts:284-315`）。多层要引入闭包表或递归 CTE，收益不明。
- **保留 `UNIQUE(owner_id, normalized_name)`**：同名文件夹是纯粹的困惑源；`normalized_name = name.toLocaleLowerCase('en-US')`（`material-library.ts:96-98`）。创建同名返回已有（`created:false`）而不是报错，这个语义也保留。
- **保留 `ON DELETE RESTRICT`**：删除文件夹必须先清空材料（`folder_id = NULL`），这是**有意的两步**——让「删文件夹」不可能顺带删材料。RESTRICT 也是 claim 搬迁时「目标夹先建、材料再指、源夹最后删」这个语句顺序的强制来源（`owner-materials.ts:879-1022`）。
- **新增 `material_folders(owner_id, id)` 的覆盖索引**其实由 PK 提供，无需额外索引；`owner_material_owner_folder_idx` 保留（`owner-materials.ts:312-314`）。

### 3.4 `agent_session_material_links`

保持现有形状（`session-material-links.ts:53-60`）：

```sql
CREATE TABLE agent_session_material_links (
  session_id  TEXT NOT NULL REFERENCES agent_sessions(id) ON DELETE CASCADE,
  material_id TEXT NOT NULL,
  created_at  DOUBLE PRECISION NOT NULL,
  PRIMARY KEY (session_id, material_id)
);
```

- **刻意不建 `material_id` 外键**：link 要跨 owner claim 存活，而 claim 会改 `owner_material.owner_id` 但**不改 id**，所以外键本可以成立；不建的理由是「悬空 link 必须能被读到并答 unavailable，而不是让删除材料的事务被外键挡住」。这条要在迁移备注里写清，否则后人会「顺手补上」。
- **不记 owner**：每个读当场 join `agent_sessions.owner_id = owner_material.owner_id`（`session-material-links.ts:144-152`）。不一致就不答——这是 claim 期间唯一正确的行为。
- **挂载 vs 库材料必须保留区别**：
  - 「库材料」= owner 名下的东西，生命周期与 owner 绑定，删除是人的动作；
  - 「挂载」= 某会话当前可见的集合，删除挂载不影响材料。
  - 统一成「一个会话一个私有材料目录」会把「同一份资料被多门课引用」变成复制，重复抽取、重复占配额，正是 owner 级抽取要消灭的（`owner-material-extraction.ts:1-58`）。

### 3.5 池的三张表（字节与保活）

`packages/@openmaic/storage/src/asset/pg.ts:167-231`：

```sql
CREATE TABLE asset_blobs (
  content_hash TEXT PRIMARY KEY,
  byte_size BIGINT NOT NULL,
  bytes BYTEA,              -- 默认字节落点
  unreferenced_at TIMESTAMPTZ
);
CREATE TABLE asset_entries (
  id TEXT PRIMARY KEY, principal TEXT NOT NULL,
  content_hash TEXT NOT NULL REFERENCES asset_blobs(content_hash),
  mime TEXT NOT NULL, meta JSONB NOT NULL, revision INTEGER NOT NULL DEFAULT 1,
  created_at DOUBLE PRECISION NOT NULL
);
CREATE TABLE asset_root_refs (
  root_kind TEXT NOT NULL, root_id TEXT NOT NULL,
  asset_id TEXT NOT NULL REFERENCES asset_entries(id) ON DELETE CASCADE,
  PRIMARY KEY (root_kind, root_id, asset_id)
);
```

- `asset_blobs` 是**内容寻址**的：同一份字节只存一次，多行共用（去重）。
- `asset_entries` 是 principal 作用域的「引用单元」；配额按 principal 求和（`material-library.ts:570-593`）。
- `asset_root_refs` 是保活根：`('material', <id>)` 在，字节就不被回收（`material-roots.ts:37`）。回收由 collector 的 entry pass 做（`packages/@openmaic/storage/src/asset/collector.ts:523,592-627`）。

### 3.6 字节到底存哪（明确回答）

| 问题 | 答案 | 依据 |
|---|---|---|
| 材料的字节应该落在哪 | **asset pool**：`asset_blobs.bytes`（默认）或 S3（配 `ASSET_S3_BUCKET` 时） | `lib/persistence/asset-byte-store.ts:11-15,263-278`；`packages/@openmaic/storage/src/asset/pg-bytes.ts:24-56` |
| `LocalMaterialByteStore` 的 root 是什么 | `resolve(process.cwd(), 'data')`，**没有 env**，进程级单例 | `bytes.ts:35-40,88-93` |
| 它还应不应该存材料 | **不应该**。统一后它只存两类东西：历史 classic 行（过渡读）、会话自己的副本字节（`text_asset_id` / `raw_asset_id`，`session-materials.ts:334-381`） | `app/api/materials/route.ts:252,361-383` |
| principal 怎么定 | `owner:<ownerId>`，纯服务端派生，拒绝空 id；`'shared'` 保留给无主素材，二者永不相撞（`'shared'` 无冒号） | `owner-assets.ts:57,62-67` |
| root 怎么定 | `root_kind='material'`、`root_id=<material id>`，每事务最多一次 `changeRoots`，principals 只用该 owner 的 partition | `material-roots.ts:37,87-149` |
| 谁来保活 | `asset_root_refs`；删材料时先 remove root 再删字节 | `material-library.ts:471-552` |

**为什么不能继续用 `<cwd>/data` 当材料字节真源**：它没有内容寻址（同内容存 N 份）、没有保活根（删行与删文件靠人排顺序）、没有配额核算（`ownerLibraryUsage` 的 pool 侧只统计 `asset_entries`，`material-library.ts:584-592`）、没有跨实例一致性（`process.cwd()` 随部署变）、也没有事务性（`finalize` 是「先写文件再改行」，中间崩溃留下孤儿对象，靠 24h sweep 兜，`owner-materials.ts:507-523`）。

**与 00-决策记录 D1 的关系（必须点明）**：D1 的结论「不做双向镜像、磁盘目录降级为导入通道」本规格完全沿用；但 D1 的前提「字节放文件系统」在今天的仓内**并不成立**——池默认把字节存进 PG 的 `asset_blobs.bytes`。所以 D1 里「文件系统存字节是主流」这条论据，对「池」这条路径不适用；真正需要文件/对象存储时，仓里已有的开关是 `ASSET_S3_BUCKET`（S3），不是 `data/` 目录。本规格的建议是：**统一走池，不新引入一个文件系统字节层**；大文件压力用 S3 开关解决。

### 3.7 owner 作用域怎么保证（两把栅栏的语义）

| 面 | 函数 | 锁 | 退役处理 | 返回 |
|---|---|---|---|---|
| 请求面（人要写的） | `fenceOwnerWrite(tx, ownerId, stageId?)` | 该 owner 的**共享** advisory lock（事务第一条语句） | 读退役表，`canonicalizeOwner !== ownerId` 就 throw `OwnerRetiredError`（403） | `void` |
| 后台面（worker 续跑） | `forwardOwnerWrite(tx, ownerId)` | 同上 | 读退役表，退役则返回**新 ownerId**，否则原样返回 | `Promise<string>`（**可能变**） |

语义要点（`owner-merges.ts:11-27,308-325`）：

1. **必须是事务第一条语句**。所有写者都把这条锁当第一条锁，于是「写持有 claim 需要的行、又在等 claim」这种死锁不可能出现；写要么在 claim 前提交（会被搬走），要么在 claim 后跑（看到 id 已退役）。
2. **共享 vs 排他**：普通写取共享锁（互相不阻塞），claim 取排他锁。所以 claim 会等所有在飞的写；写最多等 `OWNER_WRITE_LOCK_WAIT_MS`，超时答 `OWNER_BUSY`（503 + retry-after 2）。
3. **返回的 ownerId 可能变**，所以后台面拿到 `forwardOwnerWrite` 的返回值后，必须用**返回值**去派生 principal、去 WHERE，而不是用入参（`material-roots.ts:87-149` 的 `ownerId = forwardOwnerWrite(...)` 就是这个形状）。
4. **退役只对匿名 owner 生效**：`mayBeRetired = principalFromStoredOwner(id).kind === 'anonymous'`（`owner-merges.ts:220-222`）；对非匿名 owner，退役表里有记录也**不拦**，`canonicalizeOwner` 会直接 throw 说明这是配置错误（`:196-207`）。
5. **键的派生必须在 JS 里做**（sha256 前 8 字节 → bigint），不能依赖 `hashtext()`；配额锁用 `hashtextextended(...,0)` 的 64 位版本，因为 32 位会因碰撞挡住无关 owner（`owner-materials.ts:594-651` 注释）。
6. **锁按 id 升序取**（`owner-merges.ts:141-167`），两个 claim 不会互持。

### 3.8 会话挂载与库材料：保留区别（不变式）

- I5：link 只指向 `kind='source'` 且 `status='ready'` 且未删的行（`session-material-links.ts:400-463` 的 `FOR SHARE` 校验 + 数量不等即 `unavailable`）。
- I6：衍生物绝不单独挂载；通过 `derived_from` 到达（`LINKED_MATERIALS`，`:155-161`）。
- I7：一个失败全挂：attach 是「要么全挂上、要么一个都不挂」。
- I8：link 的有效性在每个读当场判定（join 双方 owner）；claim 搬 owner 后旧 link 仍有效，因为 id 不变。

## 4. 文件型材料如何并入：二选一

### 4.1 两个选项

| | (a) 一次性导入 PG，目录此后只作 drop folder | (b) 目录保留为只读镜像 + 显式同步 |
|---|---|---|
| 真源 | PG | 目录（PG 是投影） |
| 写入方向 | 目录 → 导入 → PG；PG → 导出 → 目录 | 双向，但写只允许经同步器 |
| 冲突处理 | 不需要：导入是「新增/覆盖一条材料」的显式动作 | 需要：文件改了 vs 库里改了 vs 两边都改；mtime 与内容哈希打架 |
| 删除传播 | 不需要：删库不影响盘；盘上删文件只是下次导入少一条 | 需要：删库要删盘、删盘要删库，任一侧失败就分叉 |
| 多实例 | 天然一致（PG 锁） | 每个实例都要看到同一块盘 + 同一份 mtime |
| 人去编辑器改 Markdown | **保住**：改完点「导入」（或跑导入命令） | 理论上是卖点，实际要解决上面三行 |
| 实现成本 | 一次导入脚本 + 一个导入 API（幂等键 `(owner_id, sha256)`） | 常驻 watcher/定时对账 + 冲突 UI + 删除传播 + 回滚 |
| 失败模式 | 导入时 sha256 变了 = 新版本；旧版本仍可读 | 镜像漂移：盘上的和库里的都不是「真」的，且没人能说清 |

### 4.2 推荐：(a)，并把「编辑器改 Markdown」拆成三条明确通路

推荐 (a)，理由与 00-决策记录 D1 一致且更硬：**双向同步没有一个成熟的冲突模型可抄**，而本项目的维护面只有一个人；同时 (a) 并不剥夺手改能力，只是把「改」变成显式动作。

保住「人去编辑器里直接改 Markdown」的三条通路：

1. **导入通道（drop folder）**：`OPENMAIC_MATERIALS_DIR` 保留，但语义改为「待导入区」。人往里丢/改 Markdown 文件，然后触发一次导入（CLI 或库页按钮）。导入按 `(owner_id, sha256)` 幂等：内容没变 = no-op；变了 = 新 revision（保留旧行做历史，或覆盖 `display_name` 与 `asset_id`，二选一在实现卡里定）。**读路径不再碰这个目录**。
2. **导出 → 改 → 再导入**：库页「导出为 Markdown」把一个 / 一批材料写到目录（或 zip），人在编辑器里改，再走通路 1。这是 D1 已经写的单向闭环。
3. **只读物化视图（可选，明确不是镜像）**：如果确实需要「文件一直在那儿」，可以在每次写入后把正文物化一份到目录，命名带 `material_id` 前缀，**只写不读**。任何对它的修改都不会回流，除非走通路 1。这样「打开就能看」保住，「改了自动生效」明确放弃。

**不选 (b) 的具体代价**（写给未来的自己）：要回答「文件被删了、库里那行怎么办」「库里改名了、文件名跟不跟」「同一文件在两台机器上被改成不同内容取哪个」「导入到一半崩溃怎么恢复」四个问题，每个都需要一个持久化的同步状态表（路径、mtime、hash、last_synced_revision），最后长出来的是一套弱化版分布式文件同步——与「一个人维护」不相容。

### 4.3 具体并入步骤（实现卡可直接照做）

1. **盘点**：扫 `OPENMAIC_MATERIALS_DIR`，按 `^[a-z0-9][a-z0-9-]{0,63}$` 收主题文件，INDEX.md 不入库（它是索引，不是材料）。
2. **建容器**：给 owner 建一个约定文件夹 `材料库`（`normalized_name='材料库'`），或用 `folder_id = NULL`；二选一，建议前者，避免和历史 Unfiled 混在一起。
3. **逐文件入库**：一行 `kind='source'`、`mime='text/markdown'`、`original_name='<topic>.md'`、`display_name=<INDEX.md 里的标题，取不到就用 slug>`、`bytes=len`、`sha256=digest`、`asset_id` = 池 entry（`publishOwnerMaterialUpload` 同款两段式：先 allocate 再 publish）。
4. **幂等**：先按 `(owner_id, sha256)` 查已有行；命中则跳过（或更新 `display_name`）。
5. **切换读路径**：`listMaterialText()` / `resolveMaterialsIndex()` / `listMaterialTopics()` 改为读库（subject to 3.10 的 token 预算）；`read_materials` 工具改为按 material id 读。
6. **停写**：`update_materials` 工具改为「写库 + 可选同时导出到目录」，或直接下线（agent 写材料的需求由库的 rename/move 覆盖）。
7. **保留目录**：仅导入/导出用，README 写明「改动不会被自动读取」。

## 6. 风险与不知道

### 6.1 已确认的风险

1. **池的字节在 PG 里**（默认 BYTEA）：库体积、WAL、备份都会跟着材料涨。`pg-bytes.ts:1-6` 自己写明「Deployments should size their asset limit with that replication and backup volume in mind」。如果课程材料是几百 MB 级，这条会成为主要成本 —— 未知数见 6.2。
2. **迁移链不可重放**：v2 DROP `asset_id`、v5 又 ADD（`owner-materials.ts:230-232` 与 `:266-278`）。老库的实际列状态取决于跑过哪几版，写 v6 前必须先 `\d owner_material` 实测，不能按代码推断。
3. **删除语义二选一没定**：真删（`deleteOwnerMaterial`）与墓碑（`deleteMaterial`）今天并存。统一后建议**墓碑**（可恢复、link 悬空可解释），但这会让 `owner_material` 只增不减，需要配套清理策略。
4. **`asset_id NOT NULL` 的切换窗口**：回填未完成就 ALTER 会立刻违约。必须两版迁移。
5. **文件型库的读失败静默**：`listMaterialText()` 返回空串不抛（`:100-111`）。改成读库后，这个「保命」语义要重新决定：建会话时库查询失败，是失败整个建会话还是给空库？建议给空库 + 记一条 warn。
6. **裸文本直出是安全漏洞**（D6）：并入 PG 不自动修复它；围栏必须在读侧统一加。
7. **多实例下 `OPENMAIC_MATERIALS_DIR` 无一致性保证**：路径按 `process.cwd()` 相对，各实例可能指向不同目录。导入通道必须要求绝对路径并在启动时校验。

### 6.2 不知道（明确不猜）

- **存量数据规模**：不知道有多少 classic 行、多少 `oss_key` 字节、池里已有多少材料。没有数据库访问，也禁止访问。`migrate-to-pool` 的 `scanned/migrated/skipped*` 报告是唯一会给出答案的地方。
- **线上是否配了 `ASSET_S3_BUCKET`**：不知道。若已配，池字节在 S3，6.1-1 的担心不成立。
- **`owner_material` 在真实库里的实际列集合**：不知道（迁移链有 DROP/ADD），必须以 `\d` 为准。
- **文件型库现在有没有真实内容**：不知道（`data/` 目录在，但 `OPENMAIC_MATERIALS_DIR` 指向哪、里面有没有文件，未查）。
- **`material_chunks` 是否一期就要**：取决于 D3 的检索是否同期落地；本规格只留表位，不建。
- **`kind='web'` 的写入者是谁**：只看到值域里有，没追到写入点；并入时若无人写，可考虑合并进 `source`（需要一次数据核对）。
