## 1. 一句话结论

**最终只留一套 worker：owner 级 token 链（`lib/server/material-extraction/owner-extraction.ts` + `lib/persistence/owner-material-extraction.ts`）。** 它已经是唯一同时具备「行级 claim token、claim 预算、结果原子发布、图片衍生物、池内字节、owner 级缓存」的链，也是 agent 侧读路径已经认的那一套。

另外两套的去向不同：

1. **session 链（`lib/server/material-extraction/runner.ts`）直接废掉**——它今天**没有生产者**：会话内「上传源材料」的 `createSourceMaterial` 在 `lib/`、`app/` 里只有定义（`lib/server/agent-runtime/session-materials.ts:200`），全仓唯一出现是测试里的 mock（`tests/agent-runtime/materials-route.test.ts:15`）；会话材料只剩 web 抓取（自带正文）与音频剪辑。它服务的是 RFC #1716 之前的存量副本行，属于「排空后删除」，不需要迁移能力。
2. **classic owner 链（`lib/server/materials/extraction.ts`）不能立刻删**——它今天仍是**默认上传路径**的抽取者（`app/api/materials/route.ts` 不带 `?scope=library` 时走 `oss_key` + `finalizeOwnerMaterial(...,{extract})`，写 `status:'extracting'`，见 `lib/persistence/owner-materials.ts:659-681`）。但它降级为**存量只读适配器**：新写入一律走池（`publishOwnerMaterialUpload` 已自动写 `pending`，`lib/persistence/owner-materials.ts:719-768`），classic 只为「已经处于 extracting/ready 的老行」保留一次性的重抽/回填，回填完就停掉它的扫描器。

一句话的次序：**先切上传默认走池 → 再给 classic 行做一次性 token 化回填 → session 链排空即删 → classic 扫描器最后停。** 顺序反了就有行永远没人抽（见故障模式 F4）。

**表读出来的三条硬事实：**

1. 三条链的 claim WHERE 互斥（`extracting` vs `pending`/`running`），所以**同一条行今天不会被两条链同时认领**；真正的重复抽取来自「同一份字节在 session 行与 owner 行各有一份」（同 sha256，两套缓存互不可见）。

## 3. 状态机统一

### 3.1 最终状态全集（5 个）

`idle | pending | running | done | failed`——即 token 链今天已有的全集。

映射（只用于读旧数据，不再用于写入）：

| 旧值 | 新值 | 读法 |
|---|---|---|
| `extracting` | `running` | 读时等价；但**写库不再产生这个词** |
| `ready` | `done` | 文本在 byteStore，经 `readClassicText` 适配 |
| `extraction.resultKey` 存在 | `done` 的 legacy 结果 | `readOwnerMaterialText` 的 fallback 分支 |

### 3.2 流转图（文字版）

```
                     ensureExtraction（idle|failed 且未删且 kind=source）
 idle ──────────────────────────────────────────────► pending
   ▲                                                    │
   │                                                    │ claimNext（mint token, claims+1）
   │                                                    ▼
   │                                                 running
   │                                                    │
   │        settle(failed, retryable, claims<max)       │
   └──────────────── pending ◄──────────────────────────┤
                                                        │ settle(failed, terminal 或 claims=max)
                                                        ▼
                                                      failed ──ensureExtraction（Retry，claims=0）──► pending

 running ──lease 过期（now-lease_at > ttl，别的实例）──► running（新 token，claims+1）
 running ──settle(done)──► done（终态；结果与衍生物同一事务发布）
 running ──claim 丢失（heartbeat=false / token 变了 / 行删了）──► 无状态变更；本 attempt 只能 release 或丢弃结果
 running ──优雅停机（signal aborted）──► pending（releaseExtraction：token=NULL, lease_at=0，**claims 不退还**）
 done/failed ──删材料──► （行删；池 entry 由根回收，无需状态）
```

### 3.3 幂等点（今天就有、必须保留的）

1. **ensure**：`UPDATE ... WHERE status='ready' AND deleted_at IS NULL AND COALESCE(extraction->>'status','idle')='idle'|'failed'`（`owner-material-extraction.ts:204-239`）——重复调用第二次 `queued=false`，且 claims 只在这里清零。
2. **claim**：每次 claim 新 mint token，`extraction_claims` 在**同一条 UPDATE** 里自增（`owner-material-extraction.ts:271-292`）——不可能出现两个有效 token；旧 token 的所有写都会 0 行。
3. **heartbeat**：`WHERE id AND extraction_token=$2 AND status='running'`——重复调用是幂等的（只推 lease_at），丢了返回 false。
4. **settle(done)**：`publishOwnerMaterialExtraction` 在 token 与 `status='running'` 双条件下写，且 donor 要 `result.revision === donor.revision`（`owner-material-extraction.ts:460-510`）——同一 claim 重复发布第二次返回 `not-authorized`，不会覆盖。
5. **settle(failed)**：同样的 token 条件，retryable 且 `claims<max` 才回 pending（`owner-material-extraction.ts:343-384`）。
6. **发布原子性**：`extraction`/`extraction_result`/`extraction_cache_key` 的 UPDATE、衍生物 INSERT、`changeRoots` 全在 `withMaterialRoots` 的同一事务里（`owner-material-extraction.ts:414-547`）——不存在「有结果没衍生物」或「有衍生物没结果」。
7. **缓存复制**：只复制已 `done` 且 revision 对得上的 donor；`imagesNotDownloaded` 时 `cacheKey=null`，永不复用（`owner-extraction.ts:310-447`）。

### 3.4 崩溃后能恢复的点

| 崩在哪 | 谁恢复 | 代价 | 证据 |
|---|---|---|---|
| claim 之后、抽取中 | 租约过期（60s）后别的实例接手，claims+1 | ≤60s 空窗；最多 3 次 | `owner-material-extraction.ts:256-319` |
| 心跳丢失（事件循环阻塞） | 新 claim 换 token；旧 attempt 的 publish 返回 `not-authorized` 并释放已分配的池 entry | 双跑一段时间的算力；不产生重复结果 | `owner-extraction.ts:583-645`、`449-477` |
| settle 事务中途 | 事务回滚，行仍 running，60s 后重试 | 一次重跑 | `owner-material-extraction.ts:414-547` |
| 已写入池但未发布 | 池 entry 无人引用，按分配过期回收 | 临时占配额 | `owner-extraction.ts:257-298` |
| 优雅停机 | `stopped.abort` → 运行中的 run 走 signal.aborted 分支；**token 链今天不 release** | 60s 空窗（classic 会 release，`extraction.ts:558-645`） | `owner-extraction.ts:681-732` |
| claims 用尽 | claim 循环直接写 `failed`+`processing_interrupted` | 需人 Retry | `owner-material-extraction.ts:271-292` |

## 5. 统一后的接口

放在 `lib/persistence/owner-material-extraction.ts`（持久层）+ `lib/server/material-extraction/owner-extraction.ts`（执行层），签名如下（**示意，不是已实现**）。

### 5.1 `ensureExtraction(materialId, opts)`

```ts
ensureExtraction(
  withTransaction: WithTransaction,
  materialId: string,
  opts: { fence: 'request' | 'background'; reason?: 'upload' | 'retry' | 'wait' | 'backfill' },
): Promise<{ status: OwnerExtractionStatus; queued: boolean } | null>
```

语义：
- owner 由行自己解析（不再要调用方传 ownerId，避免 fence 与 owner 不一致）；
- 只在 `idle|failed` 上生效，写 `pending`、`claims=0`、清 token/lease/error；
- `queued=false` 表示已经在队列里或已完成——**这是幂等点**；
- 不负责唤醒：唤醒是 worker 自己的扫描节奏（今天 token 链就是纯轮询，1s）。

### 5.2 `claimNext(workerId, opts)`

```ts
claimNext(
  queryable: Queryable,
  opts: {
    workerId: string;                // 只用于日志/诊断，不参与身份（token 才是身份）
    leaseTtlMs: number;              // 60_000
    maxClaims?: number;              // 3
    perOwnerLimit?: number;          // 2，对齐 classic
    exclude?: readonly string[];     // 本进程正在跑的 id
    now?: number;
  },
): Promise<{
  materialId: string; ownerId: string; token: string; claims: number;
  mime: string; originalName: string; ossKey: string; assetId: string | null;
  sha256: string; bytes: number;
} | null>
```

语义：
- 单语句完成「选行 + 判预算 + mint token + claims+1 + 置 running」，`FOR UPDATE SKIP LOCKED`；
- 候选：`pending`，或 `running` 且 `lease_at < now-ttl`；
- 预算用尽的行**不再返回**，同一语句写成 `failed` + `processing_interrupted`；
- 公平序：先按 owner 当前运行数、再按 `created_at`（照搬 `owner-materials.ts:1128-1158`）；
- `exclude` 防止本进程重领自己（今天 classic 有、token 没有）。

### 5.3 `heartbeat(claim)`

```ts
heartbeat(claim: { materialId: string; token: string }, now?: number): Promise<boolean>
```

返回 false 的唯一含义：claim 已不是你的（被接管/行删了/被重排）。**调用方必须 abort**，不能像 `runner.ts:33-40` 那样丢掉返回值。

### 5.4 `settle(claim, outcome)`

```ts
settle(
  queryable: Queryable,
  claim: { materialId: string; ownerId: string; token: string },
  outcome:
    | {
        kind: 'done';
        result: OwnerExtractionResult;     // {revision, text:{assetId,imageRefs}, derivatives, stats, extractor}
        resultBytes: number;
        cacheKey: string | null;           // imagesNotDownloaded 时为 null
        derivatives: DerivativeInput[];    // 每张图一行，同事务插入
        roots: { add: string[] };          // 文本 + 衍生物的 asset id
      }
    | { kind: 'failed'; reason: string; retryable: boolean; reasonCode?: string },
): Promise<'done' | 'retry' | 'failed' | 'lost'>
```

语义：
- `done`：走 `publishOwnerMaterialExtraction`，一个事务里 `changeRoots` + INSERT 衍生物 + UPDATE `extraction`/`extraction_result`/`extraction_cache_key`；**token 不匹配 ⇒ `lost`，不写任何东西**，调用方自己删掉已写的对象/释放已分配的 entry；
- `failed`：`retryable && claims < max` → `retry`（回 `pending`，claims 保留），否则 `failed`；
- 没有「只写结果不写状态」的旁路，也没有第二条写 `extraction_result` 的 SQL。

### 5.5 谁写 `extraction_result`

**只有 `settle(done)` 里的那一条 UPDATE（`owner-material-extraction.ts:492-506`）**。执行层（`runClaimedOwnerExtraction`）只负责：读源 → 抽取 → 分配池 entry → 组装 `result`，把写库决定权交给 `settle`。classic 的 `settleOwnerMaterialExtraction`（写 `extraction.resultKey` + byteStore 对象）在回填完成后整体删除。

### 5.6 读路径（同一套状态机的另一半）

统一后只有两个公开读函数：

```ts
readExtraction(materialId): Promise<{ text: string; revision: string; derivatives: Derivative[] }>
// 内部：extraction_result 优先；没有则 readClassicText 适配（readOwnerMaterialText 已经是这个形状）
```

- 生成链把 `readMaterialExtractionResult(record, byteStore)`（`lib/server/generation/run/services.ts:393`）换成它；
- `materialsReady`/`awaitOwnerMaterialExtractions` 的判断从 `ready|extracting` 换成 `done|running|failed`；
- 衍生物解析（`openmaic-derivative:` → `material:`）由 reader 统一做，调用方不再自己拼。

## 7. 风险与不知道

### 7.1 风险

1. **删 classic 的顺序风险**：如果先停 classic 扫描器、再切上传默认走池，中间窗口里 classic 上传的新行（`extracting`）无人抽。必须先切上传，再观察 `extracting` 行数归零。
2. **回填的语义风险**：classic 的 `ready` 结果在 byteStore 里（`data/materials/<owner>/...`），token 链的结果在池里；回填要把文本搬进池并写 `extraction_result`，图片引用格式（classic 是内联/远程 URL，token 是 `openmaic-derivative:`）不同，`text` 不能原样搬。
3. **读路径切换的回归面**：`readOwnerMaterialText` 会改写图片引用、按 revision 缓存；生成链的 `inlineRemoteImages`（`services.ts:395-420`）在 classic 结果上还要下载远程图，换 reader 后这段逻辑要重新评估。
4. **TTL 拉长的代价**：60s 租约意味着崩溃后用户最多等 60s；拉长到能覆盖 17.7s 阻塞是必要的，但再长会让 Retry 体验变差。
5. **单实例假设**：A 的 per-owner 限流靠 advisory lock 跨实例成立；C 没有锁也没有 per-owner，多实例下公平性没保证。

### 7.2 不知道

- **不知道生产库里 classic 行与库格式行的真实占比**（本机没有该库的只读连接；`DATABASE_URL` 指向的不是生产库）。
- **不知道 `withMaterialRoots` 内部是否对行加了 `FOR UPDATE`**：`publishOwnerMaterialExtraction` 里的 SELECT 没有显式锁（`owner-material-extraction.ts:430-446`），锁由 helper 的 fence/advisory lock 提供；`lib/persistence/material-roots.ts` 的锁顺序没有逐行读。
- **不知道会话文本 asset 有没有 GC**：崩溃在 `completeExtraction` 之前时，文本已写进会话 byteStore 但没有任何行引用；没找到会话资产的清扫器。
- **不知道多实例部署是否存在**（仓里没有部署清单；`instrumentation.ts` 的注释按多实例写）。
- **不知道** `document-image-parser` 的 30s worker 预算在 Node 22 与 Node 24 上的差异是否会影响 60s TTL 的余量（只读到注释，没有实测）。
- **不知道** `extraction_claims` 在生产里是否被人工改过（`ensure` 会清零，绕过预算）。
