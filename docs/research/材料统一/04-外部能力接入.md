# 04 外部能力接入规格：材料模块只做材料，能力归外部

> 勘察时间 2026-11-05 21:19 至 2026-11-06 00:30。对象：OpenMAIC upgrade/v1.3.0、DSH 插件仓、本机 pika 三技能、本机 HTTP 服务。方法：读源码与脚本（不只看文档）+ 对允许真调的服务做最小调用（单次 ≤60s）。本文件只描述接口与设计，不改生产代码。
>
> 前置：00-决策记录.md 的 D2（材料库与个人知识库分开）、D3（关键词优先，向量只做兜底）、D4（MinerU 主用）、D5（切块 2000 字符）、D8（不上 rerank）已经拍过。本文不推翻它们；只在实测接口与它们冲突的地方标出冲突，并给出修订建议。

## 1. 一句话结论

材料模块负责**材料的生命周期与证据链**：收（上传/引用）、存（字节 + 行）、抽（调度与重试）、找（检索与排序）、读（分页 + 围栏）、删（顺序与孤儿清理）；外部能力只负责**它已经做得更好的那一步**：MinerU 负责“把文档变成结构化 markdown”，bge-m3 负责“把文本变成 1024 维向量”，manage-personal-knowledge / obsidian-vault-notes 负责“个人知识根与 Vault 里的笔记”，pdf-problem-search 负责“在 PDF 书架上定位到页码”。

两者之间只通过**有超时、有降级、只读优先**的接口相连；任何外部能力挂掉，材料模块都必须留下“能收、能读、能按名字搜”的最小集合。

### 1.1 分工边界（谁负责什么）

| 事情 | 归谁 | 材料模块的义务 | 材料模块**不**做的事 |
|---|---|---|---|
| PDF/docx/pptx 解析成 markdown + 块 | MinerU（8010 兼容层） | 选它、传对参数、设超时、失败降级 | 自己写解析器、自己调 MinerU 的 /v1/* 原生接口 |
| 文本向量化 | bge-m3（Ollama 11434） | 只在需要时调用、批量、缓存、失败不影响热路径 | 自己加载模型、自己起推理进程 |
| 个人笔记的读写与版本 | obsidian-vault-notes + Vault | 只读引用、标源、标 stale | 反向写 Vault、替用户改笔记 |
| 个人知识根的配置与索引 | manage-personal-knowledge | 读它的 sqlite、调它的 CLI、遵守只读契约 | 改它的 schema、写它的库、抢它的锁 |
| PDF 书架的题目级定位 | pdf-problem-search | 只读查询、拿页码证据 | 重建它的 FTS、写它的 pdf_docs/pdf_pages |
| 材料的元数据与字节 | OpenMAIC 自己（PG + asset pool） | 唯一权威 | 把材料“寄存”在 Vault 或 Library 里当唯一副本 |
| 课程语料检索 | 8720（L4 文档层） | 可选调用、只读 | 把 L4 当材料库、再建一份同样的全量索引 |
| 网页抓取 | 8730（真浏览器） | 只在“人明确要求导入某 URL”时用 | 放进自动抽取链、批量爬取 |

一句话记法：**MinerU 是“解析器”，bge-m3 是“向量器”，pika 是“个人知识的房东”，材料模块是“课程材料的房东”**。两个房东之间可以互相介绍租客，但不合并房产。

### 2.1 bge-m3（Ollama，127.0.0.1:11434）

**调用方式**：HTTP POST /api/embed。模型名 bge-m3:latest（也可写 bge-m3）。无鉴权，本机回环。

```json
POST /api/embed
{"model": "bge-m3:latest", "input": ["第一段", "第二段"]}
```

返回：

```json
{
  "model": "bge-m3:latest",
  "embeddings": [[0.01, -0.02, "... 1024 维 ..."]],
  "prompt_eval_count": 503,
  "total_duration": 383857300,
  "load_duration": 134928100
}
```

**实测读数**（2026-11-05，Ollama 以 OLLAMA_MODELS=D:/OpenBiliClaw/bge-m3-seed 启动）：

| 项 | 读数 | 说明 |
|---|---|---|
| 维度 | 1024 | 与 bge-m3 官方一致；向量 L2 范数实测 1.0 |
| 模型体积/量化 | 1,157,672,605 B，F16，embedding_length 1024 | /api/tags 读数 |
| 冷启动 | 5.574s（1 条） | 首次加载模型 |
| 暖机 | 3 条 0.185s；32 条 0.42s | 批处理明显更划算 |
| 长文本 | 4000/8000/16000 汉字均报 prompt_eval_count=2048 | **静默截断到 2048 token**；不报错 |
| 500 汉字 | prompt_eval_count=503 | 中文约 1 字 = 1 token |
| 模型不存在 | HTTP 404 `{"error":"model \"nope\" not found, try pulling it first"}` | 失败态可判别 |
| 服务未起 | 连接拒绝（DSH embed_texts 返回 ok:false，error 为 fetch failed） | 调用方必须自己探活 |

**限制与坑**：

1. **2048 token 是硬上限且静默**。这不是“建议值”，是把 4000/8000/16000 字符都压回 2048 的实测结果。任何超过约 2000 汉字的块，后半段等于没进向量。切块必须 ≤1800 字符（中文），英文可按 4 字符/token 放宽，但统一按字符上限最安全。
2. Ollama 的 /api/embed 是**单进程串行**推理；并发请求会排队，不会并行加速。批量 32 是实测的甜点，不要按“每条一个请求”打。
3. 无鉴权、只绑回环；不要把它暴露到 0.0.0.0。
4. 这是 **DSH 工具 embed_texts 的同一后端**，但生产代码不应依赖 DSH 工具（见第 5 节）；OpenMAIC 应自己发 HTTP。

**证据**：DSH 插件 openmaic-local-capabilities/lib/index.js:210-233（embed_texts 的请求形状与 300s 超时）；实测命令与读数见第 7.2 节。

### 2.2 MinerU（8000 原生 / 8010 兼容层）

**为什么有两个端口**：MinerU 4.0.10 只提供 /v1/* 原生 REST；OpenMAIC 打的是旧版 /file_parse 形状。8010 的 compat shim 做转换：/file_parse → /v1/uploads + /v1/parse/jobs → 拼回旧形状。server-providers.yml:13-17 的注释写得很清楚，mineru.baseUrl 指向 8010 而不是 8000。

**调用方式**（OpenMAIC 现有客户端，lib/pdf/pdf-providers.ts:727 起）：

```
POST http://127.0.0.1:8010/file_parse
Content-Type: multipart/form-data
files=@<file>;type=<mime>
parse_method=auto
backend=pipeline
return_content_list=true
return_images=true
```

返回：

```json
{"results": {"hw2.pdf": {
  "md_content": "## PDE, HW 2 ...",
  "content_list": [{"type": "page_number", "bbox": [0.781,0.059,0.794,0.072], "content": "1", "page_idx": 0}],
  "images": {},
  "backend": "pipeline"
}}}
```

**实测读数**：

| 项 | 读数 | 说明 |
|---|---|---|
| 上游健康 | GET :8000/v1/health → 200，version 4.0.10，output_formats 含 markdown/middle_json/structured_content/zip | 原生接口 |
| 小 PDF | hw2.pdf（13,878 B）→ 200，2.11s，md_content 461 字符，content_list 5 块，images 0 | 暖机后 |
| 首次调用 | 18.4s | 含上游冷启动/模型加载 |
| 失败态 | text/plain 上传 → 502 `{"error":"上游解析失败: {...job failed...}","detail":"compat shim"}` | 错误体可读，但 status 502 不细分原因 |
| 轮询 | POLL_TIMEOUT 默认 1800s，POLL_INTERVAL 2s（mineru_compat.py:58-59） | 长文档可能等 30 分钟 |
| 并发 | compat 是 uvicorn 单进程、async handler（mineru_compat.py:255） | 没有队列；并发靠 OpenMAIC 的抽取队列控制 |

**限制**：

1. OpenMAIC 侧上传上限 50MB（lib/server/agent-runtime/config.ts:129，OPENMAIC_AGENT_MAX_UPLOAD_BYTES）；抽取结果上限 100MB（lib/server/materials/extraction.ts:303，OPENMAIC_MATERIAL_EXTRACTION_MAX_RESULT_MB）。
2. 同步抽取工具超时 15 分钟（lib/agent/runtime/tool-timeout.ts:44），而 compat 允许 30 分钟——**两者不一致**。走工具同步抽取时，长文档会在工具层先断，上游还在跑，结果被丢弃；后台 owner 队列不受这个 15 分钟约束，但也没有自己的单任务 deadline。建议统一：同步工具与后台任务都用 15 分钟 deadline，compat 的轮询上限也压到 15 分钟（或工具超时提到 30 分钟，二选一，不能两头各说各话）。
3. MinerU 只对“能解析的文件”返回 200；扫描件/图片走 OCR 能力（capabilities.ocr=true），但 OCR 质量本次未测。
4. images 返回的是文件名到内容的映射；DSH 的 pdf_to_markdown 会把 data:image 替换成占位符，OpenMAIC 则应把图片落成衍生物（现有提取链已做）。

**证据**：lib/pdf/pdf-providers.ts:155（getMinerUBackend，默认 pipeline）、:727-800（FormData 与错误映射）；lib/document/mime.ts:159（MINERU_SELFHOST_MIMES）；server-providers.yml:13-17；mineru_compat.py:58-59、:255；实测见第 7.3 节。

### 2.4 PDF 书架：pdf-problem-search

**定位**：不是“PDF 存储”，是**题目/定理级定位器**。输入一句数学陈述，输出“在哪本书第几页、证据窗口是什么”。

**调用方式**：

```
python scripts/math_locate.py \
  --query "Liouville theorem for subharmonic functions bounded above" \
  --db C:/Users/asus/AppData/Local/manage-personal-knowledge/library.sqlite3 \
  --limit 3 --json --max-response-bytes 8000
```

**实测**（0.48s）：

```json
{
  "schema_version": "math-locate/v1",
  "status": "ambiguous",
  "results": [{
    "title": "hw2",
    "path": "开源资源/分析学基础/布朗大学PDE习题以及解答/hw2.pdf",
    "pdf_page": 1,
    "printed_page": null,
    "match_type": "near-exact",
    "confidence": "medium",
    "verified": false,
    "statement_window": "PDE, HW 2 ... Liouville's theorem does not hold for subharmonic functions ...",
    "why": ["keeps bounded-set condition", "matches 4/4 signature terms"]
  }]
}
```

**限制**：

1. `--db` 必填；`--limit` 3–30；`--max-response-bytes` 1024–262144（默认 12288）。
2. **只读**：problem_search.py:3243、:3394 以 `mode=ro` 打开 SQLite。材料模块也不该写它。
3. 只覆盖 library.sqlite3 里已索引的文档；未索引的 PDF 要走 direct_pdf_search.py 回退。
4. 结果里的 `verified` 可能是 false；技能文档要求核验 top-3 再报“exact”。
5. 不提供“全文检索接口”——要全文用 library-search；要页码证据用 math_locate。

**证据**：scripts/math_locate.py:29-42（--query/--db/--limit 3-30/--json/--max-response-bytes 的 argparse）；problem_search.py:3243、:3394（`sqlite3.connect(f"file:{db}?mode=ro", uri=True)`）；SKILL.md 的“核验 top-3 再报 exact”规则。

### 2.5 三个基础服务：PostgreSQL 5433、课程检索 8720、真浏览器 8730

**PostgreSQL 5433**：

- 连接串：`postgres://postgres:postgres@127.0.0.1:5433/postgres`（.env.local:3）。
- 勘察时 5433 **未监听**；psql 在 D:/PostgreSQL-OpenMAIC/pgsql/bin/psql.exe。
- 扩展目录实测 248 个扩展，**没有 vector/pgvector**；有 cube、pg_trgm、btree_gin 等。
- 材料模块的硬依赖：owner_material、material_folders、asset pool 都在 PG。PG 挂了，模块不可用——这不是“外部能力降级”，是“宿主挂了”。

**课程检索 8720**（源码实测，服务未启动）：

- GET /health → `{ok, courses, builtInSec, queries, layers:{L0..L4}}`。
- GET /search?q=&layer=auto|L0..L4&topk=1..20（默认 6）；q 空 400；layer 非法 400；异常 500；结果带 elapsedMs。
- GET /document?offset=&limit=；单次最多 60000 字符，带 hasMore/nextOffset。
- L4 是**本地文档层**：把 Library 与 知识库 一起索引（build_doc_layer.py 的 ROOTS 就是这两个），3116 篇 → 82,745 块；cache/emb_L4.npy 141,058,176 B、emb_L4.ids.json 1,096,593 B。

- **它已经在索引同一批 Library/知识库文件**——这是材料模块不能“再建一套全量索引”的关键理由（见 3.4）。

**真浏览器 8730**（源码实测，服务未启动）：

- POST /browse `{"url": "...", "maxChars": 40000, "waitMs": 1500}`；maxChars 1000–120000；waitMs 0–8000；导航超时 30s。
- 返回 `{ok, title, text, ...}`；失败 `{ok:false, error, reason}`，HTTP 仍 200。
- 自带 SSRF 防护：只允许 http/https；拒绝 127/8、10/8、172.16/12、192.168/16、169.254/16、::1、fc00::/7、fe80::/10；每次重定向重新检查。
- 它不是“文档解析器”；抓回来的是网页正文，不是结构化块。

**证据**：course_rag_server.py:300-360（/health、/search、/document 的参数与错误码）；course_search.py:271（OLLAMA 与 MODEL=bge-m3）；browse_server.py:48-49（MAX_CHARS_CAP=120_000、NAV_TIMEOUT_MS=30_000）、:256-260（maxChars 与 waitMs 的钳制）。

## 3. 接入设计

### 3.1 抽取器插件化

#### 3.1.1 现状（已比“只有一条路”好，但还不够）

OpenMAIC 已经有 DocumentExtractorProvider 接口（lib/document/types.ts:53-71）：

```ts
interface DocumentExtractorProvider {
  id: string;
  displayName: string;
  supportedMimeTypes: readonly string[];
  capabilities: { text; images; tables; formulas; layout; ocr; async };
  requiresServiceConfig?: boolean;
  version: string;
  extract(input: DocumentExtractorInput): Promise<DocumentArtifact>;
}
```

问题不在“有没有接口”，在**选择逻辑太薄**：

- registry 是静态数组（lib/document/extractors/registry.ts:6-10），没有运行时注册 API；加一个抽取器要改代码 + 改 manifest + 改测试。
- 候选排序只有一条规则：`configured` 的排前面，其余按 manifest 顺序（lib/server/material-extraction/extract.ts:101-112）。
- 没有“输入体积/页数”参与选择；没有“已抽过且版本一致就复用”的选择输入；没有健康探测；没有成本档位。
- manifest 与 registry 靠 tests/document/extractor-registry.test.ts 双向锁定——这个约束要保留，否则客户端算不出 expected extractor。

#### 3.1.2 目标接口（增量，不推翻现有）

在现有 DocumentExtractorProvider 上补可选字段；extract 只加一个**可选**第二参 ctx，旧 provider 不实现也不会被破坏（TS 允许少写参数，调用方传了也会被忽略）：

```ts
export type ExtractorCost = 'local' | 'network' | 'gpu';

export interface ExtractorHealth {
  ok: boolean;
  checkedAt: number;
  latencyMs?: number;
  reason?: string;
}

export interface DocumentExtractorProvider {
  // ...现有字段...
  /** 越大越先试；同分再比 cost/体积。默认 0。 */
  priority?: number;
  /** 成本档位：local（进程内）< network（本机 HTTP）< gpu（MinerU/云）。 */
  cost?: ExtractorCost;
  /** 单文件体积上限；超过就跳过这个 extractor。 */
  maxInputBytes?: number;
  /** 2s 内探活；没有实现就视为 unknown，不阻塞选择。 */
  probe?(): Promise<ExtractorHealth>;
  extract(input: DocumentExtractorInput, ctx?: ExtractorContext): Promise<DocumentArtifact>;
}

export interface ExtractorContext {
  signal: AbortSignal;
  deadlineMs: number;
  onProgress?: (p: { stage: string; percent?: number }) => void;
}
```

注册 API：

```ts
registerDocumentExtractor(provider: DocumentExtractorProvider): void
```

约束：

1. 注册必须在模块初始化期完成（Next.js 的 route 可能多进程，运行时动态注册不可靠）。
2. 每个 provider 必须有 manifest 条目；registry 同步测试继续跑，防止客户端/服务端漂移。
3. 新增 extractor 不改调用方；调用方只认 `getDocumentExtractorProviders()` 返回的排序结果。

#### 3.1.3 选择规则（按 mime + 体积 + 是否已抽）

输入：`mime`、`bytes`、`pageCount?`、`requiredCapabilities`、`alreadyExtracted{status, cacheKey, extractorId, version}`、`health`、`userPreference`。

算法：

```
1. 若 alreadyExtracted.status=done 且 cacheKey 命中（sha256 + mime + id@version + options）
   → 直接复用，不调用任何 extractor。
2. 过滤 supportedMimeTypes 不含 mime 的。
3. 过滤 requiredCapabilities 不满足的（例如要 tables/formulas 就排除 unpdf）。
4. 过滤 maxInputBytes < bytes 的。
5. 过滤 probe().ok=false 的；若**全部**候选都探活失败，直接 failed(extractor_unavailable)，
   不要拿一个已知挂掉的服务去撞超时；只有“未实现 probe”（unknown）不算 down。
6. 排序：priority desc → cost asc（local < network < gpu）→ manifest 顺序。
7. 依次尝试；每个 attempt 独立超时；可重试错误才换下一个。
```

**规则表**（一期）：

| 输入 | 首选 | 次选 | 说明 |
|---|---|---|---|
| text/markdown | plain-text | — | 自包含，零依赖；UTF-8/UTF-16 BOM 已处理 |
| PDF ≤ 8MB，且不要求 tables/formulas | unpdf | mineru | 快、无外部依赖；文本层够用 |
| PDF > 8MB，或要求 tables/formulas/layout | mineru | unpdf（降级） | MinerU 出结构化块；失败退纯文本 |
| docx/pptx/xlsx | mineru | 无（失败即报） | 只有 MinerU 支持 |
| png/jpeg/webp/gif/bmp/jp2 | mineru（OCR） | 无（失败即报） | 不要静默返回空文本 |
| 扫描 PDF（文本抽取为空） | mineru（OCR） | 无 | 先跑 unpdf，文本 < 阈值再升级 MinerU |
| 已抽且 cacheKey 一致 | 复用 | — | 版本变更才重抽 |
| 音频/视频 | 现有 media 链 | — | 本文不展开 |

**体积阈值 8MB 是待标定的初值**，不是实测结论。现有代码没有这个阈值；建议先按 8MB 跑一版，记录 unpdf 失败率再调。

#### 3.1.4 幂等与失败链

- 复用键：`ownerExtractionCacheKey(source.sha256, source.mime, `${id}@${version}`, options)`（lib/server/material-extraction/owner-extraction.ts:215-225）。options 里必须包含 MinerU 的 backend（owner-extraction.ts:319-320 已对 mineru 加 backend）。
- 失败分类：
  - `extractor_unavailable`（连接拒绝/探活失败）→ 换下一个候选；全失败则 failed，reasonCode 可读。
  - `extractor_rejected`（MinerU 502、格式不支持）→ 不重试同一个文件；标记 failed，提示“换格式或换抽取器”。
  - `timeout`（同步工具 15 分钟；后台任务也建议设同一 deadline，今天没有）→ failed，`retryable=true`，但不要自动无限重试；最多 3 次（对齐 lib/persistence/owner-material-extraction.ts:73 的 MAX_OWNER_EXTRACTION_CLAIMS=3）。
  - `too_large`（>50MB 上传 / >100MB 结果）→ 直接拒绝，不排队。
- 并发：按 owner 2 个（现有 perOwnerLimit=2）；MinerU 是单进程，建议全局 in-flight ≤1（或 2，视 GPU 内存），不要让队列把 MinerU 打爆。
- 进度与取消：把 ctx.signal 透传到 fetch/子进程；删除材料时先 abort，再按 D7 顺序清理。
- 顺带修文案：material-prompt.ts:25 还写“每页约 8000 字符”，实际 read_material 的窗口是 materialFulltextThresholdChars() 默认 30000（config.ts:26、:37-45）。这类过期提示会让模型多翻几页，建议随抽取器改造一起改掉。

### 3.2 向量检索

#### 3.2.1 明确推荐：关键词主路径 + 向量兜底，不做混合排序

| 方案 | 推荐 | 理由 |
|---|---|---|
| 纯关键词（BM25/FTS + ILIKE） | **主路径** | 教学材料是词表匹配语料；00-决策记录 D3 引用的基准里 keyword 与 hybrid 的 top-10 完全一致；零额外失败面 |
| 纯向量 | 不推荐 | 数学/公式材料上嵌入语义稀薄；2048 token 截断会丢后半段；服务挂了整条检索瘫 |
| 混合排序（RRF/加权） | 一期不做 | 收益在词表匹配语料上实测为零，代价是每次问答多一次向量查询；等出现 5 条以上“换个说法就搜不到”的案例再开 |
| 关键词 + LLM 查询扩展 + 向量兜底 | **推荐** | 关键词保底；查询扩展解决“换个说法”；向量只在关键词空/低分时补召回；向量挂了只降召回率 |

落地顺序：

1. 一期：`search_materials` 保持现有 literal 扫描 + 名字 ILIKE；加 LLM 查询扩展（可选）；加“全文直读阈值”（≤30000 字符直接给全文）。
2. 二期：内容关键词从“逐块 literal 扫描”升级到 PG FTS（to_tsvector/tsquery 或 pg_trgm），仍然是关键词主路径。
3. 三期：仅在关键词返回 0 或最高分低于阈值时，调 bge-m3 做向量召回；结果标 `degraded.vector`，不参与主排序。

#### 3.2.2 若开启向量：参数

| 参数 | 值 | 依据 |
|---|---|---|
| 维度 | 1024 | 实测 |
| 相似度 | cosine（写入前 L2 归一化，查询也归一化，点积即 cosine） | 实测向量范数 1.0 |
| 切块 | 结构边界优先；目标 800–1200 字符；硬上限 1800 字符；overlap 150–200 | bge-m3 2048 token 截断；中文 1 字≈1 token；D5 的 2000 字符对中文已贴近上限 |
| 切块策略 | PPT 按页、Markdown 按标题、PDF 按 MinerU block 边界；结构优先于长度 | D5 |
| 批量 | 32 条/请求 | 实测 32 条 0.42s；单条请求最浪费 |
| 模型版本 | 记录 `bge-m3:latest` + 维度 + 归一化方式 | 换模型必须全量重建 |

**与 D5 的冲突要写明**：D5 定 2000 字符，理由是英文 ≈600 token；但中文 2000 字 ≈2000 token，已经贴着 2048 的上限。建议把“向量切块”的上限定为 1800 字符（中文安全），而“展示/全文切页”仍可用 2000。两个数字服务两个目的，不要混用。

#### 3.2.3 存储与增量

**存储选型**：

- 首选 pgvector：`embedding vector(1024)`，HNSW 索引（`vector_cosine_ops`）。但本机 PG **没有安装 vector 扩展**（实测 248 个扩展里没有），启用前要装扩展并重启 PG——这是一次运维动作，不是代码开关。
- 未装扩展时的过渡：`embedding real[]`（或 `float4[]`）+ 精确点积扫描。材料库规模小（几百到几千块），精确扫描足够；不要为此引入独立向量库（D3 已否掉）。
- 不选：Qdrant/Milvus/Chroma——多一个进程、多一份备份、多一个失败面；几十万向量以内 pgvector 足够。

**表结构（示意）**：

```sql
CREATE TABLE material_chunk (
  material_id   text NOT NULL REFERENCES owner_material(id) ON DELETE CASCADE,
  revision      text NOT NULL,
  chunk_index   int  NOT NULL,
  start_char    int  NOT NULL,
  end_char      int  NOT NULL,
  text          text NOT NULL,
  sha256        text NOT NULL,
  embedding     real[] ,              -- 或 vector(1024)
  model         text NOT NULL,
  policy        text NOT NULL,        -- 切块策略版本
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (material_id, revision, chunk_index)
);
```

**增量**：

1. 抽取完成（settle done）后发一个后台任务，不在上传请求里同步做。
2. 按 `material_id + revision` 生成块；每块算 sha256。
3. 已有相同 sha256 的块直接复用向量；新块才调 bge-m3（批量 32）。
4. 新 revision 全部成功后再删旧 revision；失败保留旧 revision，检索继续用旧的。
5. 删除材料时按 D7：先 abort 抽取 → 删 chunk → 删字节 → 删行。
6. 换模型/改切块策略：`policy`/`model` 不匹配的块视为 stale，后台重建；不要原地混用。

#### 3.2.4 与 ILIKE / FTS 共存

- **ILIKE 只用于名字与元数据**：material display_name、original_name、folder.name、mime。现有 lib/persistence/material-library.ts:152 与 lib/persistence/session-material-links.ts:297-300 就是这个用法，保留。
- **内容检索**：一期保持 literal 扫描（lib/server/agent-runtime/material-tools.ts:823），二期换 PG FTS；ILIKE 不要拿来做正文，`%...%` 在大文本上必然全表扫。
- **向量只在关键词之后**：关键词有结果就不调向量；关键词空/低分才调。返回结构加 `degraded: {vector: 'unavailable'|'skipped'|'used'}`，调用方知道这次结果是怎么来的。
- **不合并排序**：一期不做 RRF；向量结果作为“补充召回”附在关键词结果后面，标 `match: 'vector'`，不改变关键词排序。

### 3.3 个人知识根对接

#### 3.3.1 是不是一个东西：不是

| 维度 | 课程材料库 | Obsidian Vault | PDF 书架 |
|---|---|---|---|
| 权威存储 | PG 行 + asset pool 字节 | 磁盘 .md 文件 | 磁盘 PDF + library.sqlite3 索引 |
| 谁写 | 材料模块（上传/导入/删除） | 用户 + obsidian-vault-notes | 用户放文件 + mpk index 扫 |
| 生命周期 | 抽取、修订、删除、保留策略 | 用户随时改 | 用户随时增删 |
| 检索 | 名字 ILIKE + 内容扫描（将来 FTS/向量） | obsidian_local_kb 索引 | pdf_page_fts |
| 权限/归属 | owner_material.owner_id | 本地文件系统 | 本地文件系统 |
| 版本 | extraction revision（抽取版本，不是内容版本） | Git（本机 Vault 实测无 .git） | 文件 mtime/size |

结论：**两个东西**。材料库是“课程材料的账本”，Vault 是“个人笔记的工作区”。可以互相引用，不能互相替代。

#### 3.3.2 同步方向与冲突

**只做单向引用，不做双向同步**：

```
Vault 笔记 ──(人明确“加入材料库”)──> owner_material 行（source_kind='vault'）
                                      source_path（相对 Vault 根）
                                      source_sha256 / source_mtime_ns
                                      ↓
                              抽取结果 + revision（材料库自己的）
```

规则：

1. **默认 reference，不 copy**：材料行只存路径 + sha256 + mtime；字节留在 Vault。只有用户明确“复制进材料库”时才 copy 到 asset pool。
2. **Vault 永远赢**：笔记改了，材料行检测到 sha256 不一致 → 标 `source_stale`，不自动覆盖 Vault，也不自动重抽（重抽是用户动作或后台低优先级任务）。
3. **删除不传播**：Vault 里删了笔记 → 材料行标 `source_missing`，保留已抽文本可读；材料库删材料 → 绝不删 Vault 文件。
4. **冲突判定用内容哈希，不用 mtime**：mtime 会被同步工具/编辑器改；sha256 才是内容身份。
5. **不回写**：材料模块不提供“把材料写回 Vault”的自动路径。若用户要“存成笔记”，走 obsidian-vault-notes 的显式编辑动作，且由人确认。
6. **不做镜像**：00-决策记录 D1 已经否掉双向镜像；这里沿用同一理由（冲突合并/删除传播/哈希打架）。

**OBSIDIAN_LOCAL_KB_ROOT**：只在调用 pdf-problem-search 子进程时注入（integrations.py:452 的做法）；材料模块不要把全局 env 改掉。

#### 3.3.3 KB 资源 ID 的现状与用法

- 设计：`KB-[A-Z2-7]{26}`，registry.sqlite3 的 resources 表有 resource_id / relative_path / sha256 / content_version / status。
- 实测：resources 0 行、note_documents 0 行、note_references 0 行——**这套体系在这台机器上还没启用**。
- 所以一期用 `source_path + sha256` 做材料的外部身份；等 registry 有数据后，再加一个可选的 `kb_resource_id` 列，通过 `resource-resolve` 把 KB ID 解析成路径。
- 不要把 KB ID 当主键：它今天可能是空的；也不要自己生成 KB ID（会与注册表的校验/唯一性冲突）。

### 3.4 PDF 书架对接

**结论：复用它的索引做“定位”，不复用它做“材料存储”，也不在 Library 上再建一套全文索引。**

| 问题 | 决定 | 理由 |
|---|---|---|
| 课程材料要不要复用 pdf-problem-search 的索引？ | **要，但只读、只用于定位** | 它已经有 2422 篇 / 59301 页的 FTS 和页码证据；重建一份是重复劳动 |
| 要不要把 Library 的 PDF 再抽一遍进材料库？ | **默认不要** | 同一批字节会被抽两次、索引两次；L4（8720）已经在索引这两个根 |
| 材料库自己的索引建在哪？ | 只建“不在 Library/Vault 里的上传材料” | 避免三份索引（mpk FTS、L4、材料库）盖同一批 PDF |
| 从书架“加入材料库”怎么做？ | reference 模式：path + size + mtime；抽取时直接读磁盘 | 不复制字节；删除材料不影响书架 |
| 怎么去重？ | path + size + mtime（pdf_docs 没有 sha256 列） | 没有内容哈希，做不到强身份；这是已知弱点 |
| 页码证据从哪来？ | math_locate（题目级）或 library-search（全文级） | 两者都只读；不要自己解析 PDF 找页码 |

**材料行的来源标记**（建议字段）：

```
source_kind: 'upload' | 'library' | 'vault' | 'url'
source_path: 相对 Library / Vault 根的路径（upload 为空）
source_sha256: 能算就算（upload 必有；library 只能算一次并缓存）
source_mtime_ns: library/vault 用于 stale 检测
```

**边界**：如果一份 Library PDF 被“复制进材料库”（用户明确要求），则它有了独立字节和独立 revision；此后书架上的原文件变更**不会**自动同步——这是 copy 模式的语义，要在 UI 上写明。

### 4.2 降级后仍可用的最小集合

**PG + asset pool + plain-text/unpdf + 名字 ILIKE + read_material** = “能收、能读、能按名字搜”。

具体能力：

- 上传 txt/md/pdf；
- PDF 用 unpdf 抽纯文本（无结构、无表格、无公式）；
- 材料列表、文件夹、改名、移动；
- 按 display_name/original_name 搜；
- 分页读全文（8000 字符/页，revision 校验）；
- 删除（按 D7 顺序，无向量步骤时跳过）。

**不在最小集合里**：docx/pptx/图片解析、结构化块、公式、表格、向量召回、Vault 搜索、书架页码定位。这些都要显式提示不可用，不能静默返回空。

### 4.3 探活与熔断

- 启动时探一次：MinerU /health（2s）、bge-m3 /api/tags（2s）、Vault 路径存在、library.sqlite3 存在、PG ping。
- 运行中失败 3 次 → 熔断 60s，期间直接走降级，不再等超时。
- 每次降级写一条结构化日志：`{dependency, operation, reasonCode, durationMs, fallback}`。
- 不要把“探活失败”等同于“能力不存在”：用户可能刚启动服务；保留手动重试入口。

## 6. 风险与不知道

### 6.1 风险

1. **MinerU 吞吐未知**：单进程 uvicorn + 单 GPU/CPU，没测并发。队列一旦堆积，15 分钟工具超时会先杀请求；需要实测 10 份并发 PDF 的 p50/p95。
2. **2048 token 截断是静默的**：切块规则若被改大（比如回到 2000 汉字），后半段会无声丢失。建议在 embedding 写入前用 `prompt_eval_count` 断言 < 2048，超了记 warning。
3. **两套超时不一致**：工具 15 分钟 vs compat 1800s。长 PDF 会在工具层断，上游继续跑，浪费 GPU；要统一。
4. **PG 没有 pgvector**：三期开向量前必须装扩展 + 重启；这是一次停机动作，要写进运维步骤。
5. **Vault 索引 stale**：实测 570 篇 newer、178 篇 missing；recall 空结果不能证明“没有”。材料模块若把 Vault 当检索源，必须先刷新或明确提示。
6. **KB registry 是空的**：resources/note_documents/note_references 都是 0；任何依赖 KB ID 的设计今天都会落空。
7. **Library 没有内容哈希**：pdf_docs 只有 path/size/mtime；材料去重只能弱匹配，重命名/替换会漏。
8. **L4 与材料库重复索引**：L4 已经索引 Library + 知识库（3116 篇、82,745 块）；材料库若再抽一遍，会得到三份索引（mpk FTS、L4、材料库），存储与刷新成本翻倍。
9. **MinerU 502 错误不细分**：上游 job failed 的原因被包在字符串里；材料模块只能把 error 摘要给用户，不能自动判断“是文件问题还是服务问题”。
10. **材料正文是不可信输入**：MinerU 输出的 markdown 可能含 HTML/脚本/图片外链；进提示词前必须走 D6 的 nonce 围栏，渲染前要 sanitize。
11. **版权**：Library 里的 PDF 是用户本地资料，材料库复制/再分发要谨慎；默认 reference 模式也是出于这个考虑。

### 6.2 不知道（明确写“不知道”，不编）

- MinerU 对 docx/pptx/xlsx 的真实解析质量（本次只测了 PDF）。
- MinerU OCR 在中文扫描件上的准确率。
- MinerU 并发上限与显存占用曲线。
- bge-m3 对中英混排、公式文本的实际 token 比例（只测了纯中文）。
- pgvector 在本机 PG 版本上的安装方式与重启影响（未装、未测）。
- 8720 的 L4 索引新鲜度（last scan 时间未读到）与 emb_L4.npy 覆盖了多少块（文件 141MB ≈ 34k 向量，而块有 82,745，**不能假设全量已嵌入**）。
- 8730 在本机 Edge/Playwright 组合下的成功率（未启动、未测）。
- OpenMAIC 现有抽取队列在 MinerU 长任务下的真实吞吐（未压测）。
- Vault 697 篇笔记里有多少与课程材料主题重叠（未做内容比对）。
